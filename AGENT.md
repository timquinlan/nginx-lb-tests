# upstream-rl — Architecture & Design Notes

Phases 1-4 built: scaffolding, ACO, Markov Chain (all three paths running simultaneously), and the `analysis/` tooling. See `design-docs/upstream-rl.md` (not part of this repo) for the full project prompt. This file tracks the decisions actually made while building it, and the tradeoffs behind them.

## What's running, and where

Everything runs in Docker Compose. There are two Compose files:

- `docker-compose.full.yml` — builds and starts 5 backend containers plus the controller. Local dev / self-contained experiments.
- `docker-compose.controller.yml` — starts only the controller, pointed at external hosts listed in `upstream-hosts.txt`.

The **controller container runs NGINX itself** — there is no separate NGINX container. The controller's `entrypoint.py` validates backends, generates NGINX config, starts NGINX, primes algorithm state, and starts the per-algorithm sampling loops, all automatically on `docker compose up`. It does **not** run the traffic generator — that's a separate, manually-triggered step (see below).

## Language: Python

Controller and backend containers are both Python (stdlib-heavy, no frameworks). Chosen for fastest iteration on the ACO/Markov math and to share idioms with the Phase 4 analysis tooling (also Python). Tradeoff accepted: larger process footprint than a Go binary, which matters more once this moves toward an actual edge-device deployment — revisit then, not now.

## Entrypoint / orchestration model

`controller/entrypoint.py` runs, in order:

1. `validate_backends.py` logic — ping every host in `upstream-hosts.txt` with retries; exit non-zero on failure so `docker compose up` reports the container as failed.
2. `nginx/generate_config.py` — write `rr.upstream.conf` (static, unweighted), `aco.upstream.conf`/`mc.upstream.conf` (equal-weight placeholders), and the main server conf.
3. Start NGINX as a background child process (`nginx -g "daemon off;"`).
4. `sampler.py`'s priming run: probe every backend directly (bypassing NGINX — there's no traffic yet), compute initial weights, write them via `config_writer.py`, which triggers `nginx -s reload`.
5. Start the per-algorithm sampling loops (background threads, one per dynamic algorithm) — these run continuously for the life of the container, rewriting weights and reloading NGINX every sampling window.
6. The entrypoint process then **supervises** NGINX: it waits on NGINX's child process and forwards `SIGTERM`/`SIGINT` to it, exiting with NGINX's exit code when it stops.

**NGINX is supervised, not `exec`'d.** An earlier version of this design said the entrypoint would `exec` into NGINX as the final step (making it literally PID 1). That doesn't work: NGINX has to already be running by step 3 so step 4 can `nginx -s reload` it. A second `exec nginx` at the end would either fail (port already bound) or start a conflicting second instance. Instead the wrapper stays alive as long as NGINX does and mirrors its exit code — what actually matters for Docker's health/lifecycle model, without the literal PID-1 mechanics.

**The traffic generator is invoked manually, per run:**

```sh
docker exec <controller-container> python3 traffic_generator.py --tick 60 --rps 5 --duration 10
```

This is why `runs.log` isolates multiple runs by start/end timestamp — the setup above happens once per container lifecycle; the operator can invoke additional traffic-generator runs against the same primed, continuously-adapting NGINX without restarting anything.

**Only one `traffic_generator.py` invocation is meant to run at a time (undocumented assumption, not enforced).** `next_run_index()` picks a run's index by counting existing lines in `runs.log` and adding one -- two concurrent invocations against the same container would both read the same count and pick the *same* run index, then both send traffic to the same paths simultaneously with no way to separate one run's requests from the other's in the access logs afterward. Nothing in the code detects or prevents this; it's just not a supported way to use it. Sequential runs (one at a time, back to back) are exactly what `runs.log`'s isolation-by-timestamp is built for.

**`--tick` and `TICK_SECONDS` are not the same channel (gap found, then fixed).** `TICK_SECONDS` is read once at container boot by `sampler.py` (the sampling window size) and each backend (the degradation cycle length) — fixed for the container's whole life. `--tick` only controls the *traffic generator's own* status-line cadence and duration accounting for that one `docker exec` invocation. Since the generator runs as a brand-new process against an already-running container, there's no live channel for its `--tick` to reach the sampling loops — the design doc's "propagated... via `TICK_SECONDS`" never actually happened in the code. Passing a `--tick` that differs from the container's real `TICK_SECONDS` doesn't break anything, it just makes the generator's own "tick: N/M" printout and duration math describe a different cadence than what's actually happening underneath, which is confusing more than harmful. Fixed by defaulting `--tick`'s argparse value to `common.TICK_SECONDS` (which already reads the env var) instead of a hardcoded `60` — `docker exec` inherits the container's configured environment automatically, so leaving `--tick` unset now always matches the real sampling cadence; an explicit override remains possible for the rare case where you want them to differ.

## NGINX layout

- Experiment traffic (`/rr`, `/aco`, `/mc`) is served on a **separate port from NGINX's stock default server** (`NGINX_EXPERIMENT_PORT`, default `8080`). The base image ships `conf.d/default.conf` — a `server { listen 80 default_server; }` block. Adding our own `listen 80` server would either conflict (duplicate default server) or silently never be reached (the shipped default wins). A separate port sidesteps this and leaves port 80's default location as a free, undisturbed liveness check.
- The controller's own generated confs (`rr`/`aco`/`mc` upstream blocks + main server block) do **not** live directly in `/etc/nginx/conf.d`. A volume mounted straight onto `conf.d` would overlay — and hide — whatever the base image put there (`default.conf` included) the first time the mount is used. Instead they live in `CONF_DIR` (default `/var/lib/upstream-rl/nginx-conf.d`, bind-mounted from `./nginx-conf` on the host), and `generate_config.py` drops one small file *outside* that bind mount, directly into the real (image-backed) `conf.d`, that just does `include /var/lib/upstream-rl/nginx-conf.d/*.conf;`. Cheap to regenerate identically every startup; never touches `default.conf`.
- DNS resolver directive is chosen by `DEPLOY_MODE`: `127.0.0.11 ipv6=off` (Docker embedded DNS) for `full`, `8.8.8.8` (public resolver) for `external`. Note this directive only actually governs re-resolution for *variable*-based `proxy_pass` targets; our upstream blocks use static `server host:port;` entries, which NGINX resolves once at config-load/reload time via the normal system resolver regardless of the `resolver` directive. In practice this doesn't matter for `aco`/`mc` (reloaded every sampling window, so DNS stays fresh as a side effect) but does mean `rr.upstream.conf` — generated once, never reloaded — would keep routing to a stale IP if a full-mode backend container were recreated (not just restarted) mid-run. Not a concern under the default flow; worth knowing if that assumption changes.

## Log format and the `$upstream_addr` gotcha

Log format: `$msec | $uri | $upstream_addr | $upstream_response_time | $upstream_header_time | $status | $sent_http_x_degradation_state`.

- `$msec` is NGINX's only source of millisecond-precision timestamps — it's seconds-since-epoch with a millisecond decimal (e.g. `1721923200.123`), not a raw integer millisecond count. `$upstream_response_time` / `$upstream_header_time` are the same shape (e.g. `0.014`), despite this doc's field names using an `_ms` suffix for readability elsewhere. Multiply by 1000 if an integer ms value is wanted.
- **`$upstream_addr` is a resolved `ip:port`, never the original hostname.** `sampler.py` has to independently resolve each host in `upstream-hosts.txt` and build an `ip:port -> host` map (`common.resolve_ip_to_host_map`) before it can attribute access-log lines back to a named backend. This is re-derived at the start of every sampling window.

## Two data streams (refined)

- **Stream 1 (operational, mostly not analyzed):** algorithm internal state (raw pheromone/transition-matrix values), fallback-probe notices — stderr only, not a deliverable. **One exception, added after Phase 3**: the *applied integer weight* per backend per window is also written to `{algo}.weights.csv` (see "Per-window weight history" below) specifically so Phase 4 can use it. Everything else in Stream 1 stays stderr-only.
- **Stream 2 (the experimental evidence):** NGINX access logs + `runs.log`, on the `./logs` host directory (bind-mounted, not a Docker-managed named volume — see "Bind mounts, not named volumes" below). This remains the primary input to Phase 4 (TTFB, selection frequency, etc.) — the weight history is supplementary detail explaining *why* the selection frequency looks the way it does, not a replacement for it.

## Per-window weight history

`config_writer.apply_weights()` appends every window's applied weights to `{algo}.weights.csv` (`aco.weights.csv`, `mc.weights.csv`, separate file per algorithm) — unconditionally, whether or not the weight actually changed from the prior window, so a time series has no gaps to fill in. Priming's initial weights land as the first row for free, since priming calls `apply_weights()` the same as every later window.

**Wide-form CSV**: `timestamp_ms, timestamp_iso, <one column per backend>` — one row per window. Chosen specifically so a line chart (x=time, y=weight, one line per backend) is a direct `df.set_index('timestamp_ms').plot()` away with no pivot step first — long-form (`timestamp, backend, weight`, one row per backend per window) was tried first but rejected once the actual goal (a multi-line chart) was stated plainly, since long-form needs a reshape before you get that chart. Column order is fixed to the canonical `hosts` list from `upstream-hosts.txt`, not whatever order a given algorithm's internal dict happens to iterate that window (observed to vary window-to-window for Markov, since it depends on log-parsing order) — a wide CSV's columns have to stay stable for the life of the file. Both timestamp forms are written: epoch ms for precise sorting/joins against the access logs (which use `$msec`), ISO for a human to eyeball directly.

**Tradeoff accepted, deliberately not engineered around:** if the backend pool in `upstream-hosts.txt` changes between container restarts that both append to the same (persistent, bind-mounted) `./logs`, the column set won't match the original header partway through the file. Expectation is to clear or rename `./logs` before a run against a genuinely different backend pool — the same thing you'd want for a clean comparison anyway, not a new burden this format introduces.

Deliberately just the applied integer weight (what's actually in the `.conf` file), not the raw pheromone level or stationary probability behind it — keeps the file minimal and directly answers "what was NGINX actually doing," which is what Phase 4 needs it for.

## Bind mounts, not named volumes

`./logs` and `./nginx-conf` (repo-root directories, gitignored) are bind-mounted into the container rather than using Docker named volumes. Named volumes are opaque — reaching the data means `docker exec`/`docker cp` every time. Since this whole project's point is inspecting the experiment data (and Phase 4's analysis scripts are meant to be runnable/adaptable directly), plain host directories you can `ls`/`cat`/point a local Python script at are more useful here. Both Compose files bind-mount the same host paths by design (same "switch modes without losing data" property named volumes would have given, without the opacity).

## Phase 1 algorithm stub

`controller/algorithms/stub.py`'s `EqualWeightStub` was wired to both `/aco` and `/mc` in Phase 1, so the sampling/config-writer/change-counter plumbing was exercisable end-to-end before any ACO or Markov math existed. Left in the tree, unwired, as a minimal reference implementation of the `Algorithm` interface — Phase 3 replaced it on `/mc` with the real Markov module.

## Backend static-file stub

`backend/server.py` has a `/static` route -- the design doc's "static file stub for future throughput phase": if `STATIC_FILE_PATH` is set and points at a real file, it serves that file's bytes with a `X-Degradation-State` header like the default route; otherwise it returns `501` with a plain-text explanation rather than pretending to serve real content. No Compose file sets `STATIC_FILE_PATH` today, so in practice this route always 501s right now — the plumbing exists (env var read, file-serving code path, degradation state still applied) without being exercised by any current experiment, exactly as the design doc asked for ("design for this without implementing it now"). A future throughput-focused phase would set `STATIC_FILE_PATH` (and mount a file at that path) to turn it on; nothing else in this route needs to change.

## Backend degradation timing decoupled and randomized

Prompted directly by a methodology question, not found during review: is having the backends' degradation staircase run in lockstep with the algorithms' sampling cadence tainting the experiment?

**The coupling was real.** The original formula: `CYCLE_SECONDS = DEGRADATION_MULTIPLIER * TICK_SECONDS`, each of the 3 states (`baseline`/`+100ms`/`+250ms`) lasting `CYCLE_SECONDS / 3` -- a pure, deterministic function of elapsed wall-clock time from each backend's own process start, permanently phase-related to `TICK_SECONDS`, the exact same base unit driving the algorithms' sampling window. (Caught while investigating: the README's old timing table claimed "Staircase step duration: 1x tick," which was never actually true -- the real segment length is `cycle/3`, only equal to 1 tick when the multiplier is 3, and none of the default backends use that multiplier. Fixed alongside this change.)

**Why it mattered more than "just an artifact":** the per-request base latency genuinely is randomized (`random.uniform(MIN,MAX)` every request, unchanged) -- what was clockwork was specifically *when* degradation started/stopped. A fixed, deterministic, phase-locked pattern repeats exactly for the life of a container. That means a much longer real run (this project's stated direction: "hundreds of times longer" than a smoke test) wouldn't dilute the coupling the way more data usually dilutes noise -- it would just re-measure the same fixed relationship more precisely. The algorithms' sampling cadence and the environment's own change cadence were never actually independent variables, even though `--tick` makes them look freely adjustable.

**Fix:** `backend/server.py`'s degradation model now:
- Reads `DEGRADATION_MEAN_DWELL_SECONDS` directly (per backend, same pattern as `LATENCY_MIN_MS`/`LATENCY_MAX_MS`) instead of deriving a cycle length from `TICK_SECONDS` -- the environment's characteristic timescale is now a fixed property of the backend pool, full stop, not something that silently rescales with whatever `--tick` a given traffic-generator invocation happens to use. `TICK_SECONDS` was removed from `backend/server.py` entirely (nothing else there used it) and dropped from each backend's Compose environment.
- Draws each *visit* to a state independently from `random.uniform(0.5, 1.5) * DEGRADATION_MEAN_DWELL_SECONDS`, rather than a fixed segment. Uniform-around-the-mean, not exponential: bounded (no long tail producing an implausibly long or near-instant state), simple to reason about, and sufficient to break the fixed periodicity -- the state *sequence* (baseline -> +100 -> +250 -> repeat) and the step *magnitudes* stay unchanged; only the dwell *timing* per visit is now random. (Going further -- randomizing the sequence itself, e.g. a semi-Markov process with probabilistic transitions -- was considered and explicitly deferred; this is a narrower, cheaper fix that already removes the specific problem identified.)
- Values chosen to match the old defaults' mean at the default 60s tick (`multiplier * 60 / 3`) purely for rough continuity with earlier smoke-test runs: `backend-1`/`backend-3` (old multiplier 2) -> 40s mean; `backend-2`/`backend-4` (old multiplier 4) -> 80s mean; `backend-5` (old multiplier 6) -> 120s mean.

**Concurrency:** `current_degradation_state()` is called from a new thread per request (`ThreadingHTTPServer`), so advancing the state needs a lock now that it isn't a pure function of elapsed time alone (the old code needed no lock -- `elapsed % CYCLE_SECONDS` was stateless and safe to call from any thread with no coordination). The critical section is a few float comparisons, guarded by one `threading.Lock()`; contention is a non-issue since transitions happen at most every several seconds. It's a `while`, not an `if`: if a backend gets no traffic for longer than several dwell periods (an algorithm having deprioritized it, or a slow window), the next call has to walk through however many states it *would* have passed through by then, redrawing each one's dwell along the way, rather than advancing one step and leaving the state stale.

**Reproducibility, traded for a different kind of reproducibility.** The old deterministic clock meant the *entire* degradation schedule was computable in advance from nothing but elapsed time -- perfectly reproducible, but also perfectly predictable, which was the actual problem. Randomizing dwell times loses a-priori predictability but keeps this project's "reproducible framework" property in a different form: every realized transition is now logged to `./logs/degradation-{backend}.log` (`timestamp_ms,new_state,dwell_seconds_drawn`), a small addition mirroring `sampler.py`'s `{algo}.weights.csv` (ground truth about what actually happened, not a replacement for the request-level `X-Degradation-State` already in each access log). Reproducible via the logged realized timeline now, not via predictability in advance. This needed a new bind mount (`./logs`) on each backend service in `docker-compose.full.yml`, matching the project's existing "plain host directories, `ls`/`cat` them directly" convention (see "Bind mounts, not named volumes" above) -- scoped to `docker-compose.full.yml` only, since `docker-compose.controller.yml`'s external backends aren't Docker containers this project controls or can bind-mount into.

**Verified live, not just by inspection:** a real run showed `backend-1` (40s mean) transitioning through all 3 states within a single ~50s smoke test with dwells of 46.8s, 38.8s, 58.6s -- all within the expected [20s, 60s] range and visibly non-periodic -- while `backend-5` (120s mean) hadn't transitioned yet at the same elapsed time, exactly as expected for its longer, independently-scaled mean.

### The tunable that actually matters: dwell-to-window ratio, not an absolute dwell value

`DEGRADATION_MEAN_DWELL_SECONDS` is exposed as a single shared override in `docker-compose.full.yml` (`${DEGRADATION_MEAN_DWELL_SECONDS:-<per-backend default>}`, same pattern as `TICK_SECONDS`) specifically so this could be stress-tested quickly. Two live one-minute runs at `TICK_SECONDS=5` (5s sampling window), same rps, same duration, only the dwell config changed:

- **Differentiated defaults (40/80/120s mean, ratio 8x-24x vs. the 5s window):** `aco` vs `rr` p=1.7e-9, `mc` vs `rr` p=0, mean/median/p90/p95 significant for both. Strong, clean separation -- this is the run quoted throughout the sections above.
- **Flat 10s mean for all five backends (ratio ~2x vs. the window):** `aco` vs `rr` p=0.045 (barely under alpha), `mc` vs `rr` p=0.057 (**not** significant), almost every per-stat CI includes 0. The TTFB-over-time chart shows all three algorithms' lines moving essentially on top of each other for the entire run, just tracking the pooled degradation curve together.

**The mechanism, not just the correlation:** at a ~2x ratio, most sampling windows either straddle a transition or get invalidated by the next one before an algorithm's newly-computed weights have a chance to matter -- there's no interval in which ACO's momentum or MC's responsiveness can diverge from what round robin would have done anyway. This isn't "less variation" in a good way (more noise, more interesting data); it's the algorithms' entire mechanism of advantage getting outpaced by the environment, collapsing all three paths toward statistically indistinguishable. Requested directly by the user, who correctly read the resulting chart as "that kills the variation" rather than the richer signal a faster cycle was expected to produce.

**Why this caps the "continuity" reasoning above, not just extends it:** the 40/80/120s defaults were chosen to match the *old* formula's mean *at the old default 60s tick* -- but they're only validated here against a `5s` smoke-test window, where they land at a comfortable 8x-24x ratio. A real run using the README's standard 60s tick (60s window) would put those same defaults at a 0.67x-2x ratio -- inside the range that just collapsed differentiation above. **Conclusion: `DEGRADATION_MEAN_DWELL_SECONDS` should be chosen relative to whatever tick/window a real run actually uses, not left at these smoke-test-tuned absolute values.** Based on the two data points above (2x fails, 8x+ works), a real run should aim comfortably above the failure threshold -- e.g. at least ~8x the intended sampling window for the fastest backend class -- until a more precise threshold is mapped. Reverted to the differentiated defaults for now (decision: map the exact threshold later if needed, not before the real runs).

## Backends share a baseline, drift independently

Prompted by another methodology question: if `aco`/`mc` beat `rr`, how much of that is genuine real-time tracking of changing conditions, versus just finding whichever backend has the best fixed personality (`backend-1` 10-20ms vs `backend-5` 30-80ms) and mostly sticking with it? The original design conflated both effects -- a fixed personality creates a mostly-stable ranking, and degradation only perturbed it temporarily. An algorithm's measured advantage could come from either, with no way to separate them.

**The fix: replace the fixed 0/100/250ms staircase with a continuous, independently-drifting, signed offset.** `backend/server.py`'s degradation model now works like this:

- Each backend still has its own `DEGRADATION_MEAN_DWELL_SECONDS` reshuffle cadence (unchanged from the earlier decoupling work -- randomized dwell, independent per backend, no shared clock).
- At every reshuffle, instead of advancing through a fixed 3-state sequence, it draws a fresh offset from `random.uniform(DEGRADATION_OFFSET_MIN_MS, DEGRADATION_OFFSET_MAX_MS)` -- a **signed** value. Negative means currently faster than its own baseline; positive means slower. `total_latency_ms = max(0.0, random.uniform(LATENCY_MIN_MS, LATENCY_MAX_MS) + offset_ms)`.
- The offset range (`-10` to `+250` by default) is shared identically across all 5 backends -- only the independent per-backend *draw* differs, not the distribution itself. Asymmetric on purpose: there's more physical room for a real backend to get much worse (unbounded contention, GC pauses, noisy neighbors) than to get much better (a floor set by the network/OS stack).
- `X-Degradation-State: 0|1|2` became `X-Degradation-Offset-Ms: <signed float>` -- the NGINX log format (`generate_config.py`), `analysis/log_reader.py`'s parsing, and `analysis/analyze.py`'s chart overlay (`degradation_offset_by_window`, was `degradation_fraction_by_window`) all changed to match: the overlay now plots mean signed offset (an unbounded, zero-centered line with a reference line at 0) instead of "% of requests in a non-zero state" (which stops being a meaningful summary once state is continuous, not a 3-way enum).

**Originally staged, then collapsed straight to the shared-baseline end-state instead of narrowing gradually.** The initial plan (previous paragraph) kept personality ranges distinct for one round, reasoning that a real operator would naturally treat a wildly-slower backend as a de facto backup -- realistic, worth keeping rather than eliminating immediately. After seeing that round's results (run 17: still strong, significant separation with personality + drift combined), the user opted to skip the gradual narrowing and just go straight to a fully shared baseline instead, since the mechanism to do so (`docker-compose.full.yml`'s `${VAR:-default}` overrides) was already in place from the staged plan. **`LATENCY_MIN_MS`/`MAX_MS` are now identical across all 5 backends** (`10`/`20`, `backend-1`'s old range -- kept as the shared value mostly because it happens to match "Standard 5G (MEC Edge)" on a real edge-latency benchmark table the user found, see below). Each backend still draws fresh per-request jitter within that shared range (unchanged mechanism); the *only* thing differentiating one backend from another now, at any point in time, is the independently-drawn drift offset. `DEGRADATION_MEAN_DWELL_SECONDS` stays varied per backend even with personality gone, purely to keep the 5 backends' reshuffle timings decorrelated from each other.

**The original personality ranges turned out to plausibly already encode a real-world edge-network model, not arbitrary numbers.** Checked against a "Edge Latency Benchmarks by Connectivity" reference table the user found after the fact: `backend-1`'s old range (10-20ms) is an *exact* match to "Standard 5G (MEC Edge)" RTT, `backend-3`'s (12-18ms) is the same tier tighter, and `backend-5`'s (30-80ms) lines up with "4G LTE/Hybrid" RTT plus handover budget stacked on top. See the project-framing memory for the fuller edge-device reframing idea this opens up (handover-latency-as-the-offset-mechanism), which is being deliberately deferred while the current methodology exploration continues.

**Reverted back to distinct personalities as the default, one methodology run later.** The shared-baseline variant was run for real (run 19, 10 minutes, rps=250): both algorithms remained significantly better than `rr` (mean -6.4ms `aco`, -17.6ms `mc`), confirming they don't rely on a stable ranking to win -- a genuine, banked data point, not wasted effort. But immediately after, the user raised the sharper point this whole detour was actually in service of: if every backend performs identically on average, the honest pitch for this whole project shrinks to "just use whatever's already standard" -- there's no persistent structural difference left for adaptive weighting to earn its keep on. Distinct personalities represent a realistic heterogeneous-hardware fleet (some backends permanently weaker, e.g. older CPUs deliberately kept as low-weight backups) -- exactly the kind of persistent asymmetry a static or purely-instantaneous baseline can't see.

**"Yeah, but [X]" framing corrected same day, before it went further than a slide idea:** the original version of this argument named anycast as the thing this project needs to justify itself against. Checked directly (see project-framing memory): anycast is a public-edge/DNS/CDN technique -- mid-size-to-enterprise orgs on private/hybrid clouds do not use it for internal application traffic. The actual real-world status quo for exactly this deployment pattern (one L7 reverse proxy in front of an internal backend pool) is plain weighted round-robin or least-connections, via HAProxy/NGINX/F5 BIG-IP. That's a sharper, more answerable objection than the anycast one -- and this project already answers it directly, since `rr` already *is* that baseline and the planned NGINX `random`/`random two least_conn` additions cover least-connections too. Don't reintroduce the anycast framing without this correction.

`LATENCY_MIN_MS`/`MAX_MS` are hardcoded per backend again (not a shared override var -- a single variable can't express 5 different defaults). To reproduce the shared-baseline check, edit those 5 values directly for that run, same manual-edit workflow already used for every other backend-config experiment in this project. `DEGRADATION_OFFSET_MIN_MS`/`MAX_MS` remain shared overrides, unaffected by this reversal.

**Fully decentralized, not coordinated -- collision probability is a birthday-problem calculation, not a guess.** A synchronized alternative was considered (shared clock, deterministic seeded permutation guaranteeing no two backends ever land on the same offset) and rejected: it would have reintroduced a shared, predictable *timing* clock across backends, trading away exactly the kind of predictability the earlier decoupling work removed. Fully independent draws, no coordination, is more representative of real independent backends anyway. The actual collision risk was computed, not assumed: with each offset a continuous float (Python's `random()` effectively draws from ~2^53 distinct values) and 5 backends, the birthday-problem estimate is P(any two backends land on the exact same offset in a given reshuffle) ≈ C(5,2) / 2^53 ≈ 1.1 × 10⁻¹⁵ -- about 1 in 900 trillion, or roughly 300 million years of continuous 10s-dwell reshuffles before expecting one by chance. The user's own framing: even a 10% collision chance would have been an acceptable price for a fully decentralized model over a coordinated one, so this was never a blocking concern -- just worth knowing precisely rather than hand-waved. (The one thing that *would* break this guarantee: quantizing the offset to a small discrete set, e.g. a handful of fixed rank slots, before use -- collision probability at that point becomes a real, non-negligible fraction. Not a risk here since the offset stays a plain float end to end, same as the base latency draw already did.)

## Phase 2: ACO

`controller/algorithms/aco.py`'s `AntColonyOptimization` is now wired to `/aco` in `sampler.py`. One pheromone float per backend: every window, evaporate all of them by `ACO_EVAPORATION_RATE` (default `0.1`, i.e. retain 90%), then add `ACO_DEPOSIT_CONSTANT / latency_ms` (default constant `10.0`) — lower latency deposits more, satisfying "higher latency = less reinforcement." Weights are read off the pheromone table **relative to its current max**, not normalized to sum to 100: `weight = clamp(100 * pheromone / max(pheromone.values()))`. Sum-based normalization gets coarser as backend count grows (each share shrinks toward `1/N`); max-relative scaling keeps the top backend at ~100 regardless of pool size, so it doesn't degrade at higher backend counts (see Scaling).

Both constants are overridable via environment variables (`ACO_EVAPORATION_RATE`, `ACO_DEPOSIT_CONSTANT`) and exposed in both Compose files the same way `TICK_SECONDS` is.

**Verified with a live 20-tick (100s) run at a 5s smoke-test tick:** priming immediately separated weights by observed latency (fastest backend → 100, slowest → 71 on one run); the change counter climbed continuously (26 changes over 22 windows) rather than flatlining, confirming ongoing learning rather than early convergence; `/aco`'s backend-selection distribution diverged from `/rr`'s and skewed toward the lower-latency backends. The change counter climbing on *every* window is expected, not a bug: the staircase degradation cycles are shorter than several sampling windows, so the "true" latency ranking itself keeps shifting, and ACO (by design) never fully settles while that's happening.

## Phase 3: Markov Chain

`controller/algorithms/markov.py`'s `MarkovChain` is now wired to `/mc` in `sampler.py`, running simultaneously with ACO on `/aco`. Genuinely memoryless: `update()` holds no instance state at all between calls (contrast `AntColonyOptimization.__init__`'s persisted `self.pheromone`) — the transition matrix is rebuilt entirely fresh from that window's `observations` dict every time.

**Transition matrix construction:** `score[h] = 1 / latency_ms[h]` (lower latency, higher score), and row `i`'s outgoing probabilities are `score[j] / sum(score[k] for k != i)` for every `j != i`, with `P[i][i] = 0` — no self-transitions, so every window models moving to a (possibly different) backend, weighted toward whichever others were faster. Excluding `i` from its own row's normalization denominator is what makes each row genuinely depend on state `i` (i.e. an actual transition matrix, not just the same preference vector copy-pasted into every row, which would trivialize "transition matrix" down to "normalized inverse-latency vector with an unnecessary square-matrix wrapper").

**Stationary distribution** is computed by plain power iteration (repeated `π ← πP` from a uniform start, up to 200 iterations or until the L1 change drops below `1e-9`) — no need for `numpy`/eigen-decomposition at this backend-count scale, and it's the standard textbook method regardless of scale.

**Weight conversion is direct scaling, not max-relative like ACO:** `weight = clamp(100 * stationary_probability)`. This is deliberately different from ACO's `100 * pheromone / max(pheromone)` — a stationary distribution is already a normalized proportion-of-time-in-each-state, so scaling it straight by 100 carries that proportion directly into the weight ratios; pheromone is an unbounded accumulator that only means something relative to the current leader. Same underlying pattern (turn a per-backend score into an NGINX weight), different scaling rule because the two scores have different shapes.

**Verified with a live 20-tick (100s) run, all three paths running simultaneously:** priming produced visibly different weight distributions for ACO vs. Markov from the *same* underlying latency observations (one run: ACO gave the slowest backend a weight of 41, Markov gave it 2) — concretely demonstrating ACO's momentum vs. Markov's memoryless responsiveness described in the design doc. Both change counters climbed on nearly every one of 20 windows (23/23) — Markov's lack of any smoothing makes it at least as noisy as ACO here, arguably more so, matching "adapts quickly... noisier." All three access logs (`rr`/`aco`/`mc`) landed at exactly 501 lines each (500 requests + the traffic generator's immediate first-fire), confirming genuinely concurrent traffic across all three paths, and `runs.log` recorded both `aco` and `mc` change counts in one record.

**Noticed after Phase 3:** ACO's weights top out near 100 (max-relative scaling) while Markov's top out in the 30s (direct scaling of an already-normalized stationary distribution) — see "Weight conversion" above. This is intentional (each is the natively-correct scaling for its own algorithm's underlying quantity) but makes head-to-head numeric comparison between the two awkward. Decided, deferred to Phase 4:
- An exact-match counter between ACO's and MC's per-window confs was considered and rejected: given the scale mismatch alone, it would read zero from window 1 onward regardless of whether the algorithms actually agree or disagree — it can't distinguish "behaving similarly" from "behaving differently," so it doesn't test what it's meant to test.
- The real comparison (which specific metric TBD — candidates: top-pick agreement per window, rank correlation, or cosine/L1 distance between the two weight vectors normalized to sum to 1) belongs in Phase 4, computed post-hoc from the logged access-log data, not live in `sampler.py` — the two sampling loops are independent threads that can drift slightly out of phase, so bucketing by wall-clock time after the fact is more robust than trying to line up "iteration N of ACO" with "iteration N of MC" live.
- The actual weights written to `aco.upstream.conf`/`mc.upstream.conf` stay on their native scales (no change) — Phase 4 adds a separate, comparison-only normalized view (both rescaled to sum to 1) rather than changing what's live.

## Phase 4: Data analysis tooling

`analysis/` reads a selected run's access logs and weight-history CSVs and produces a stdout summary table plus PNG charts. See `analysis/README.md` for the log schema, run-isolation mechanics, and how to adapt it -- this section covers the architectural decisions behind it.

**`analysis/` is deliberately independent of `controller/`, not an import of it.** `analysis/log_reader.py` re-implements the small amount of parsing it needs (access-log fields, `runs.log`, weight CSVs) rather than importing `controller/common.py`, even though the two overlap conceptually. Two reasons: (1) `analysis/analyze.py` is meant to be runnable directly from the host machine against the bind-mounted `./logs` directory (the whole point of "bind mounts, not named volumes" above) -- `controller/common.py` isn't on a host Python's import path, and several of its constants (`CONF_DIR`, `HOSTS_FILE`) don't mean anything outside the container anyway; (2) the design doc's "simple enough to adapt for a different algorithm or log schema" goal is better served by `analysis/` only assuming on-disk file formats, not this project's internal module layout.

**Naming collision, caught before it shipped:** the analysis parsing module was originally also named `common.py`, matching `controller/common.py`'s naming. That's fine until `traffic_generator.py`'s end-of-run hook imports both in the same process (see below) -- Python's `sys.modules` cache is keyed by bare module name regardless of `sys.path` order, so whichever `common` module gets imported first "wins" and the second import silently returns the wrong module instead of raising ImportError. Renamed to `analysis/log_reader.py` before this ever ran, since the failure mode (subtly wrong constants/functions with no error) would have been nasty to debug. General lesson for any future module added under `analysis/`: don't reuse a name that already exists under `controller/` if the two might ever be imported into the same process.

**The end-of-run hook uses an in-process import, not `subprocess`.** `traffic_generator.py` adds `analysis/` to `sys.path` at startup and calls `analyze.run_analysis(...)` directly (see `invoke_analysis`). A `subprocess.run([...])` alternative was considered -- it would mirror how the traffic generator itself is invoked (a separate process via `docker exec`) -- but was rejected: it would pay Python + matplotlib's import cost on every single run for no benefit, and it would need to re-derive `LOG_DIR` from the environment a second time instead of just passing the already-in-scope value. Analysis failures are caught and logged rather than left to propagate, since by the time the hook runs, the traffic-generator run already succeeded and its record is already in `runs.log` -- a broken chart shouldn't be reported as a failed experiment run.

**`ip_to_host.json` -- a small addition to `sampler.py`, made to unblock Phase 4.** Attributing `$upstream_addr` (a resolved `ip:port`) back to a named backend requires the same `ip:port -> host` map `sampler.py` already builds every sampling window (see "$upstream_addr gotcha" above) -- but that resolution depends on Docker's embedded DNS, reachable only from inside the container's network. Since `analysis/` is meant to also run from the host machine directly, it can't just re-resolve `upstream-hosts.txt` itself the way `sampler.py` does. Fix: `sampler.py`'s `write_ip_to_host_snapshot()` persists the mapping it already computes to `ip_to_host.json` in `LOG_DIR` on every window (and once during priming, so it exists before the first request), and `analysis/log_reader.py` reads that file instead of re-resolving anything. This also sidesteps a subtler correctness issue a fresh host-side resolution could introduce: the snapshot reflects the exact mapping NGINX was actually using at the time, not a potentially-different one from a later lookup. Missing file (e.g. logs copied from elsewhere) degrades gracefully -- backends are labeled by raw `ip:port` instead of by name.

**Charting: matplotlib, the one dependency in an otherwise stdlib-only project.** Flagged to the user as a real fork before building: hand-rolling stdlib-only SVG line charts was the zero-dependency alternative, and CSV-only output (no charts) the simplest one, but the design doc's "line chart" outputs are an explicit deliverable, not a nice-to-have. Chosen: matplotlib. In the controller image it's installed via `apt-get install python3-matplotlib` rather than `pip` -- Debian's system Python refuses global `pip install` (PEP 668, "externally managed environment"), and matplotlib ships as a normal apt package, so this is the same install path already used for `iputils-ping` rather than a venv or `--break-system-packages` workaround. For host-side use, `analysis/requirements.txt` covers the ordinary `pip install` case on the user's own machine, which isn't subject to the container's apt/PEP-668 constraints. The `matplotlib.use("Agg")` backend is set explicitly in both plotting functions since the controller container has no display.

**Degradation overlay is pooled across algorithms, not per-algorithm.** `X-Degradation-State` is a property of the backend that served a request, not of whichever algorithm's location block happened to route to it -- the same backend in the same degraded state affects `/rr`, `/aco`, and `/mc` identically. The TTFB chart overlays one degradation-fraction line (pooled across every discovered algorithm's records in each window) rather than three separate, mostly-redundant ones.

**Per-run config-change count is recomputed from `{algo}.weights.csv`, not read off `runs.log`'s `change_counts`.** `config_writer.py`'s change counter is cumulative for the life of the container (persisted in `{algo}.state.json`), so `runs.log`'s `change_counts` for run N is a running total, not "how many changes happened during run N" -- reading it directly would double-count everything from prior runs. Instead, `log_reader.count_weight_changes()` filters `{algo}.weights.csv` to the selected run's `[start_ts_ms, end_ts_ms]` window and counts transitions between consecutive rows inside it. Accepted imprecision: a change landing exactly on the window boundary (the last row before the run started differing from the first row inside it) isn't counted, since the row-to-row diff never looks outside the isolated window. Undercounts by at most one per algorithm per run -- not engineered around, same spirit as the weights.csv column-stability tradeoff above.

**The analysis window size defaults to the run's own `tick_seconds`, inheriting the same assumption `traffic_generator.py --tick` already carries** (see "`--tick` and `TICK_SECONDS` are not the same channel" above): correct as long as `--tick` wasn't deliberately overridden away from the container's real `TICK_SECONDS` for that run. `--window-seconds` is exposed on `analyze.py` for the case where it was.

**Added after Phase 4 shipped: `runN_stats_report.txt`, the overall statistical comparison against the control.** A text file (not a chart) with TTFB mean/median/p90/p95/p99 per algorithm, plus each non-control algorithm's delta against `rr` -- `CONTROL_ALGO` in `analyze.py`, hardcoded rather than inferred, since "which path is the control" is a fact about the experiment design (the design doc: "Round robin is not part of this codebase -- it is the stock NGINX control that results are measured against"), not something derivable from which log files happen to exist. `median`/`p90`/`p95`/`p99` all go through the same `percentile()` nearest-rank function already used for the summary table's p95 (median is just its p50 case) -- factored into one `log_reader.ttfb_stats()` helper so the stdout table and this report can't quietly disagree on how a stat was computed. If a run's logs have no `rr` access log (an adapted setup with a different control), the absolute table still gets written; only the delta section is skipped, with a note rather than a crash.

**Added next: actual significance testing, not just deltas.** Prompted by the obvious follow-up question once deltas existed -- are they real, or noise. Two tests, deliberately kept separate rather than collapsed into one verdict, since they answer different questions:

- **Mann-Whitney U** (`log_reader.mann_whitney_u`) on the full TTFB samples -- "is the whole distribution different from the control." Implemented by hand (normal approximation with tie correction, `math.erf` for the CDF) rather than reaching for `scipy`: this is standard textbook material (rank sums, tie-corrected variance, continuity correction), and adding a second dependency on top of matplotlib for one function felt like the wrong tradeoff versus ~60 well-commented lines of stdlib. Runs on the *full* sample, uncapped, on purpose -- a single sort is still sub-second at real-experiment scale (measured: 0.5s at 300k+300k samples), so there's no reason to give up statistical power here the way the bootstrap below has to.
- **Percentile bootstrap confidence intervals** (`log_reader.bootstrap_delta_cis`) on each stat's delta -- "is *this specific stat's* difference likely non-zero," flagged significant when the CI excludes 0. Percentiles don't have a simple closed-form CI the way a mean does, so bootstrap resampling is the standard approach regardless of dependency budget.

**Why the bootstrap needs a sample cap and Mann-Whitney doesn't:** flagged by the user directly -- smoke-test runs are currently short (tens of seconds, ~1000 requests/path), but real experiments are meant to run "hundreds of times longer." Mann-Whitney costs one sort; bootstrap repeats that sort `n_resamples` times (default 2000) *per stat comparison*, which would stop scaling well before a real run's request count did. Fix: `capped_sample()` draws a reproducible random subsample (default cap 5000/side) before bootstrapping only -- point estimates and Mann-Whitney still see every request. Benchmarked directly (not just estimated): a 2000-resample bootstrap capped at 5000/side takes ~2s even against a simulated 300k-samples-per-side dataset, so the report's total runtime stays roughly constant regardless of how long the real run actually was. `bootstrap_delta_cis` also sorts each resample exactly once and reads all five stats off that one sort, rather than resampling separately per stat (5x fewer sorts for the same resample count).

**One knob, not two, for the significance level.** `SIGNIFICANCE_ALPHA` (default 0.05) is both the Mann-Whitney verdict threshold and, as `1 - alpha`, the bootstrap CI's coverage. Separate `--alpha`/`--ci` flags were considered and rejected: they could drift out of sync (e.g. a 95%-CI verdict sitting next to a 0.10-alpha Mann-Whitney verdict with no flag that those are two different confidence levels), and there's no real use case here for wanting them to differ.

**Reproducibility:** the bootstrap's RNG is seeded from the run's own `start_ts_ms` (`random.Random(run["start_ts_ms"])` in `run_analysis`), not the wall clock -- regenerating a report for the same run reproduces the same CIs, matching this project's general "reproducible framework" framing rather than adding run-to-run jitter a reader would have no way to distinguish from a real change in the underlying data.

**On short runs, "not significant" is the expected, correct result, not a bug.** Verified directly: the smoke-test run analyzed above (aco/mc vs rr, ~1000 requests/path, 50s) produced Mann-Whitney p-values of 0.27 and 0.14 and every per-stat bootstrap CI included 0 -- i.e., none of the 2-4% deltas earlier reports showed were distinguishable from noise at this sample size. That's the honest answer for a run this short against backends with deliberately overlapping latency ranges, not a sign anything is broken; a real (hours-long, much-higher-request-count) run is what's expected to actually separate the algorithms statistically.

### NGINX `worker_processes` pinned to 1 (bug found verifying Phase 2)

While checking `/rr`'s backend-selection distribution as an "it should be ~uniform" sanity check, it came back meaningfully skewed (178 vs 57 requests across backends, in a 501-request run) even though `/rr` is plain unweighted round robin that NGINX never touches. Cause: the base image's `worker_processes auto` had started 10 workers (one per visible CPU core on this machine), and NGINX's round-robin state — weighted or not — is kept independently *per worker process*. Each worker balances correctly on its own, but the aggregate across 10 independent counters at only ~500 total requests looked skewed. This affects `/aco` and `/mc` identically, not just `/rr` — it's a general noise floor from the process model, not something biasing one path over another.

First attempt at a fix — `nginx -g "daemon off; worker_processes 1;"` — crashed the container outright: `worker_processes` is already set in the base image's `nginx.conf`, and NGINX refuses a directive supplied both via `-g` and in the config file ("duplicate directive", exit code 1). Actual fix: `entrypoint.py`'s `pin_worker_processes()` patches that one `worker_processes auto;` line in `/etc/nginx/nginx.conf` in place (regex substitution) before NGINX starts, since the directive can't be set from our generated `conf.d` includes either (main-context only, those are `http{}`-scoped). Trades multi-core concurrency for a single, precisely interpretable round-robin/weighted state, matching this project's stated priority (reproducible measurement over raw throughput).

### NGINX's default `worker_connections 1024` is the real ceiling at high `--rps`

Found while load-testing (see README "Choosing `--rps`" for the numbers): at 500-650rps/path the controller container's CPU is the binding constraint (single core, by the `worker_processes 1` decision above). At 800rps/path, CPU spilled past 100% *and* NGINX started logging `1024 worker_connections are not enough while connecting to upstream` -- a hard connection-count ceiling, not just a busy core. Each proxied request holds two connection slots against that 1024 limit (one for the client connection, one for the upstream connection), so the practical ceiling is closer to ~512 concurrent proxied requests, not 1024. This is an ordinary NGINX tuning knob (`events { worker_connections N; }`, main-context like `worker_processes`) -- unlike `worker_processes`, raising it carries none of the round-robin-reproducibility tradeoff, since connection count doesn't affect which backend gets selected. Not raised here because CPU saturates around the same rps range regardless (see the load-test note below), so it wouldn't buy much without also revisiting `worker_processes`; worth knowing about if a future need calls for pushing throughput further.

### Traffic generator's thread pool auto-scales with `--rps` (bug found load-testing)

`traffic_generator.py`'s per-path `ThreadPoolExecutor` was originally a fixed `MAX_WORKERS_PER_PATH = 20`, sized around the 5rps default. Verified fine up to 25rps (each ~5s window logged ~120-130 real access-log lines, matching 25rps × 5s almost exactly — no fallback probes needed once traffic was actually flowing). At 500rps the fixed pool would have silently become the bottleneck: Little's Law puts the sustainable ceiling for 20 workers at roughly 130-270rps given backend latencies up to ~330ms worst-case (max latency range + top degradation step), so `--rps 500` would have quietly achieved something well under 500 with zero error or warning — `ThreadPoolExecutor.submit()` just queues faster than it drains. Fixed by sizing the pool from the requested rps instead of a fixed constant: `workers_per_path = max(20, int(rps * 0.5))` (500rps -> 250 workers/path), logged at run start so the actual pool size is visible, not silently chosen.

**Load-tested live at 500rps/path (1500rps aggregate) with the fix in place:** the controller container (NGINX + the traffic generator + the sampler loops, all sharing one container) held at ~75-79% of one core throughout a 60s run; each backend container stayed at 9-14% CPU, 12-17MB RAM — comfortably idle. Confirms the controller, not the backends, is the bottleneck at high throughput, and that bottleneck is single-core-bound by design (NGINX pinned to `worker_processes 1` for reproducibility, and the Python traffic generator is GIL-bound regardless of thread count) rather than a Docker resource limit — neither Compose file sets one, so there was nothing to "raise." Explored as a one-off curiosity, not adopted as a config change: throughput is explicitly out of scope for this project's actual measurement goal (TTFB / algorithm comparison), and raising NGINX's `worker_processes` to use more cores would reintroduce the exact per-worker round-robin skew the fix above removed. Decision: leave `worker_processes 1`, keep the thread-pool auto-scaling fix (that one's a straightforward correctness improvement independent of the throughput question).

## Phase 5: NGINX's own built-in load-balancing methods as comparison paths

Adds three more static, always-on paths alongside `/rr`: `/random` (NGINX `random`), `/random2` (NGINX `random two`), and `/leastconn` (NGINX `least_conn`). Motivation, per the project-framing correction made earlier (see "backends share a baseline, drift independently" above): the real-world "why not just use X" objection to this project isn't anycast, it's "why not just use plain weighted round-robin or least-connections, which is what enterprises actually run today via HAProxy/NGINX/F5 BIG-IP." `/rr` already covers the round-robin half of that; these three cover the rest of what NGINX ships out of the box, without writing any new controller code to do it.

**All three are static, exactly like `/rr` -- not a fourth kind of dynamic algorithm.** NGINX's own upstream-block method directive does the selection internally, every request. No weight computation, no sampling loop, no `weights.csv`, no config-change counter, no controller module. This is enforced by which tuple a name goes in: `STATIC_ALGO_NAMES` grew from `("rr",)` to `("rr", "random", "random2", "leastconn")` in `controller/common.py`; `DYNAMIC_ALGO_NAMES` (`aco`, `mc`) is unchanged. Everything downstream that already branches on these two tuples -- NGINX config generation's static-vs-placeholder-weight split, the sampler's dynamic-only sampling loops, the traffic generator's dynamic-only change-count display -- picked these three up for free, no code change needed beyond the tuple itself. `traffic_generator.py`'s `read_location_paths()` (reads paths back out of the generated NGINX config) and `analysis/log_reader.py`'s `discover_algos()` (derives the algorithm list from which `*.access.log` files exist) both picked up the three new paths automatically too, exactly as designed for "adding an algorithm should be straightforward" -- verified live, not just by inspection (see "Verified with a live run" below).

**A new kind of upstream block, not a variant of the weighted one.** `random`/`random two`/`least_conn` are upstream-block-level method directives -- an entirely different selection mechanism from the `server host:port weight=N;` lines `/aco`/`/mc` use, not a special case of it. `controller/nginx/upstream_conf.py`'s `render_upstream_conf()`/`write_upstream_conf()` gained a `method=None` parameter: when given, it's rendered as the first line inside the `upstream {}` block (e.g. `random two;`), and `weights` stays `None` for these paths (plain `server host:port;` entries, same as `/rr`). `method` and `weights` are never both set in this project, though NGINX itself would allow it. The mapping from algorithm name to directive lives in `controller/common.py`'s `STATIC_ALGO_METHODS` (`{"rr": None, "random": "random", "random2": "random two", "leastconn": "least_conn"}`), read by `generate_config.py`'s static-algo loop -- `None` for `rr` means no directive line at all, reproducing its historical unweighted conf byte-for-byte rather than writing an explicit `round_robin;` NGINX doesn't even have a directive for (round robin is just the upstream block's default with no method line at all).

**`random two least_conn` was considered and deliberately not built as a fourth, separate path.** Checked directly against NGINX's own documented behavior before implementing anything: `least_conn` is already the *default* (and, in open-source NGINX, only) method for the `two` parameter -- the only other choice, `least_time`, is NGINX Plus-only. That makes `random two;` and `random two least_conn;` byte-for-byte identical directives in behavior, not just similar. Flagged to the user before building anything (not silently picked): building both would have meant two paths that are mechanistically guaranteed to produce statistically indistinguishable results, for no informational payoff. Given the choice between (a) building both anyway as a validation check that the stats pipeline correctly reports "no difference" for two identical mechanisms, (b) dropping the redundant path and adding plain `least_conn` (no random pre-selection at all) as a genuinely distinct fourth static comparison point instead, or (c) just shipping two paths total, the user picked (b) -- `/leastconn` is `least_conn;` alone, not `random two least_conn;`. This is also arguably the more real-world-relevant addition anyway, per the corrected "plain least-connections is what enterprises actually run" framing this whole phase is answering to.

**Default `--rps` lowered from 250 to 125, same day, at the user's request -- before any load-testing was redone.** Doubling the path count (three static, three original) at the old default would have pushed aggregate request load to ~1500rps, roughly double what the README's `--rps` ceiling numbers (~650rps/path, measured with only three paths) were ever validated against. Halving the per-path default to 125 keeps aggregate load (~750rps across six paths) at the same level those original measurements cover -- a deliberate "match the old validated aggregate, don't assume a new one" choice, not a fresh benchmark at the time it was made.

**Since validated live, same day: a real 60s smoke test (run 20) and a full 10-minute run (run 21, 60 ticks x 10s, ~75k requests/path) both completed with zero lines in every `*.error.log`** -- no `worker_connections` warnings, no dropped requests, across all six paths simultaneously at 125rps/path. The three new static paths' expected "cheap as `/rr`" behavior held in practice, not just in theory. The 10-minute run also resolved the "might need roughly double the run duration for the same statistical power at the lower rps" concern raised when the default was first lowered: it wasn't needed -- nearly every stat (mean/median/p90/p95, for every non-control algorithm) came back significant at `alpha=0.05`, only isolated `p99` comparisons stayed inside their CI's zero-crossing (matching this project's already-documented pattern of p99 being the noisiest tail stat at any sample size, not a duration problem specific to this run). Concretely, at 10 minutes/125rps: `leastconn` beat `rr` by -23.7% mean TTFB, `random2` by -15.4%, `mc` by -14.2%, `aco` by -8.1%, and `random` stayed statistically indistinguishable from `rr` (p=0.21) -- exactly the "random and rr should track each other, everything else should separate" shape the design predicts. `leastconn` beat `mc` (best built-in vs. best adaptive) with p=0 on the overall distribution, though the practical mean gap there was smaller (+12.5% for mc, i.e. mc trailing leastconn) than either's gap to `rr`.

**`analysis/analyze.py`'s stats report gained two sections, both scoped by the user ahead of implementation:**

1. **Every discovered algorithm ranked best-to-worst**, not just each vs. the `rr` control individually. `rank_algos()` sorts algorithms with TTFB data by mean TTFB (ascending -- lower is better); algorithms with no data are omitted from the ranking rather than sorted last with a placeholder, since there's nothing to rank. Tags each entry `[control]`/`[adaptive]`/`[built-in]` so the ranking itself is legible without cross-referencing which group is which.
2. **An incremental comparison between the best-performing static/built-in algorithm and the best-performing adaptive algorithm (`aco`/`mc`)** -- not just everything against the single fixed `rr` control. Once there are multiple built-in candidates (`rr`/`random`/`random2`/`leastconn`) and multiple adaptive candidates (`aco`/`mc`), the existing per-algo-vs-`rr` comparisons never directly say which of each *group* actually won; this picks the top of each group (by the same ranking) and runs the same Mann-Whitney U + bootstrap-CI machinery already used for the control comparisons, just between those two specific algorithms instead of each-vs-`rr`. Which algorithm names belong to which group is hardcoded (`ADAPTIVE_ALGO_NAMES = ("aco", "mc")` in `analyze.py`, everything else discovered is "built-in") -- same reasoning as `CONTROL_ALGO` being hardcoded rather than inferred: group membership is a fact about the experiment design, not derivable from which log files happen to exist.

**This new section is deliberately *not* gated on `rr` having data, unlike the existing control-comparison section.** The original per-algo-vs-control loop returns early (skipping straight to writing the file) if `rr`'s access log has no data for the run. The new ranking and best-built-in-vs-best-adaptive sections are computed and appended to the report *before* that early-return check, so they still appear even if `rr` itself is missing -- `rr` is just one of four possible "best built-in" candidates now, not a prerequisite for this specific comparison the way it is for the rr-control section.

**Terminology used throughout this phase's documentation** (README's "The algorithms," this section): described along an information-used/memory-horizon ladder -- none (`rr`, `random`) -> live instantaneous state (`random two`'s/`leastconn`'s connection counts) -> historical, no memory (`mc`) -> historical, with persistent decaying memory (`aco`) -- and separately noting *where* each one's unpredictability (if any) enters: at the selection mechanism itself (`random`/`random two`, a literal dice roll) vs. upstream in the environment feeding an otherwise-deterministic weight-update rule (`aco`/`mc`, whose *rule* is reproducible but whose *input* -- backends' randomly-generated latency -- isn't). Deliberately avoids a flat deterministic/non-deterministic binary, which conflates "is the selection step itself random" with "is the resulting behavior over time predictable" -- these have different answers for `aco`/`mc` (rule: yes; behavior: no) and only the second is true for `random`/`random two` (mechanism: yes, from the very first request).

## Phase 6: multiple workers, kept correct with shared-memory zones

`worker_processes` moved from `1` to `4` (`WORKER_PROCESSES_COUNT` in `controller/entrypoint.py`), and every upstream block now carries an NGINX `zone` directive (`DEFAULT_ZONE_SIZE = "64k"` in `controller/nginx/upstream_conf.py`, one uniquely-named zone per algorithm -- `rr_zone`, `random_zone`, etc. -- rendered unconditionally, not opt-in). Motivation: reproducible single-worker measurement was trading away real throughput headroom the controller container otherwise has (see the existing `worker_processes 1` writeup above, and the CPU-headroom numbers in the README, both single-core-bound by that pin) -- and a shared zone turns out to remove the reason that tradeoff was necessary in the first place, not just compensate for it.

**Diagnosed live, before any code changed, specifically to understand the mechanism rather than assume it.** Manually edited `/etc/nginx/nginx.conf` and `rr.upstream.conf` inside the running container (not through the generator -- a deliberately temporary, reverted-afterward experiment) and sent 100 real requests at 10rps to `/rr` at each of three configurations, tallying `$upstream_addr` -> backend from the access log:

| Config | backend-1 | backend-2 | backend-3 | backend-4 | backend-5 | spread |
|---|---|---|---|---|---|---|
| 2 workers, no zone | 23 | 22 | 19 | 18 | 18 | 5 |
| 6 workers, no zone | 29 | 22 | 17 | 16 | 16 | 13 |
| 6 workers, **with zone** | 22 | 20 | 20 | 19 | 19 | 3 |

Confirms the mechanism directly: more workers without a zone means more independent round-robin cycles (NGINX keeps this state per-worker by default), each one biased toward whichever backend it's currently pointed at when its share of requests lands -- and since every fresh worker's cycle starts from the same first-configured server, the *aggregate* skew gets worse, not better, as worker count goes up. A `zone` directive puts that state in memory shared across all workers instead, collapsing the aggregate back down close to even -- residual bias toward `backend-1` remained even with the zone, expected and predicted before running it: at only 10rps/100 requests there still isn't enough traffic for a single shared cycle to fully wash out its own start-of-cycle skew. This same per-worker-state mechanism applies identically to `least_conn`'s live connection counts and `random two`'s least_conn tiebreak (both live, instantaneous, worker-local without a zone) and to `aco`/`mc`'s `weight=`-based selection state -- not just plain round robin -- which is why the zone directive was added to *every* upstream block, unconditionally, rather than only `/rr`'s.

**Implementation is unconditional/always-on by design, not a configurable opt-in.** `render_upstream_conf()` in `controller/nginx/upstream_conf.py` renders the `zone` line for every algorithm's upstream block regardless of `method`/`weights`, immediately after the opening `upstream NAME {` line. No parameter to disable it was added -- every algorithm path needs correct cross-worker state the same way, there's no case in this project where skewed per-worker state would be preferable. Zone name is derived per-algorithm (`zone_name()`, e.g. `mc_zone`) so each path's shared state stays independent of every other path's, matching the existing per-algorithm `upstream_name()` pattern. 64k was picked without needing to tune it: NGINX's per-server shared-state footprint is on the order of a few hundred bytes, nowhere near 64k even at the 25-backend scale mentioned in "Scaling" above.

**A `zone` directive is compatible with every selection method used in this project** (plain round robin, `weight=`-based weighted round robin, `random`, `random two`, `least_conn`) -- this isn't an NGINX Plus feature; the `zone` directive itself has been available in open-source NGINX since 1.9.0 for exactly this kind of shared dynamic upstream state.

**Verified live after implementing, not just by the manual pre-diagnosis above.** Rebuilt the container (`worker_processes 4` confirmed live via `/proc` inspection, since the base image has no `ps`), confirmed all six generated `.upstream.conf` files carry their `zone` line, then ran a full 60s traffic-generator run (run 22, all six paths, 125rps/path): zero lines in every `*.error.log`, `/rr`'s selection-frequency chart came back visibly flat/overlapping across all 5 backends (a tighter result than the 100-request manual diagnostic above, as expected -- far more requests per shared cycle to average out any residual start-of-cycle bias), and the relative algorithm ranking held steady (`leastconn` still best, `random` still statistically tracking `rr`). **Unexpected bonus, not the point of this change but worth recording:** mean TTFB dropped noticeably across every single path compared to the equivalent single-worker run at the same `--rps` (e.g. `rr`: ~146ms at 1 worker vs. ~105ms at 4 workers, same 125rps/path) -- with the CPU bottleneck spread across 4 cores instead of 1, there's simply less request queueing delay baked into every path's measured TTFB. This is a real, useful side effect (more real headroom before hitting the `worker_connections` ceiling discussed in the README), not a confound in the *relative* comparisons between algorithms, which are still measured against each other within the same run.

**CPU headroom re-measured after the fact, prompted by a direct question: why isn't `docker stats` showing something closer to 400%?** With `worker_processes` at 4 and no CPU limit set on either Compose file, four fully-saturated NGINX workers could show up to ~400% in `docker stats` (`docker info` on the dev machine used here reports 10 host CPUs, so the theoretical container ceiling is ~1000% -- `docker stats`' CPU% is per-logical-core, 100% = one core saturated, `(container CPU delta / system CPU delta) * NCPU * 100`, confirmed against NGINX/Docker's own documented formula before trusting the numbers below). Measured live at two points: **250rps/path (the restored default, ~1500rps aggregate) held around 84-85% CPU; 500rps/path (~3000rps aggregate, double the default) held around 130%, with zero errors in any `*.error.log` at either rate.** Both are far under the ~400% ceiling four saturated workers could reach -- this isn't a sign of a bottleneck, it's a sign NGINX's own per-request proxying cost is genuinely cheap here (no TLS, small payloads, event-driven I/O that spends most of its time in `epoll_wait` rather than burning CPU) relative to what the *old* single-worker measurement (~91-95% CPU at 650rps/path, 3 paths) suggested the ceiling would be. That old number reflected a single core doing all the proxying *and* competing with this same container's other CPU consumers (the traffic generator's own Python process, the sampler loop's background threads) -- once proxying is spread across 4 workers, the picture changes enough that the old figure isn't a reliable predictor of the new one.

**Flagged directly, not assumed: this is two measured points, not a linear model.** 500rps/path (2x the 250 default) produced ~130% CPU, not ~170% (2x 84-85%) -- CPU-vs-rps here doesn't scale proportionally in either direction, consistent with fixed per-worker/per-connection overhead (event-loop bookkeeping, connection setup/teardown) not scaling linearly with request rate the way pure per-request compute would. Don't interpolate a `--rps` value between these two points and assume the CPU% in between is a straight line -- if a specific intermediate rate matters, measure it directly the same way these two were (`docker stats --no-stream` sampled mid-run).

**`--rps` default moved twice in direct response to this measurement, same session: 125 -> 250 -> 500.** 125 was picked conservatively when `/random`/`/random2`/`/leastconn` were first added, before the worker/zone move existed to justify a higher number; 250 followed once the multi-worker move landed. Once 250 itself measured at only ~84-85% CPU (not the ~170% a naive 2x-of-125 extrapolation might have suggested), the user proposed testing 500rps/path directly rather than settling at 250 -- it also happens to approximate a sustained ~1B-hits/month production load, double the ~500M/month the original 250 figure was chosen to approximate back when this project ran 3 paths on 1 worker. 500rps/path confirmed clean (zero errors, ~130% CPU) via live spot-checks (`docker stats --no-stream` sampled mid-run) before being adopted as the new default -- a full 10-minute run at 500 was started immediately after to confirm this holds over a sustained period, not just a brief spike; see the run's own `runN_stats_report.txt` under `./logs/analysis/` for the completed results (by the time this line is read, that run should already be finished and its stats report the authoritative record, not this paragraph's live-spot-check numbers).

**Killing an in-progress run to change defaults, done cleanly via SIGTERM, not a hard container restart.** The 250rps/path 10-minute run was still active when 500 was proposed. Rather than discard it silently or leave it running while a second run started concurrently (which `traffic_generator.py`'s own `next_run_index()` doesn't support -- see AGENT.md's existing "only one invocation at a time" note), it was stopped mid-flight: found the `traffic_generator.py` process's PID via `/proc` (no `ps` in this minimal image) and sent it `SIGTERM` via `python3 -c "import os, signal; os.kill(pid, signal.SIGTERM)"` (no `kill` binary in this image either). `traffic_generator.py`'s existing signal handler (`handle_signal`, already wired for graceful `docker stop`/`Ctrl-C` handling) caught it, drained in-flight requests, and wrote a normal run record with `"interrupted": true` and a shorter-than-planned `actual_duration_s` -- exactly the same graceful-shutdown path already documented for `SIGTERM`/`SIGINT`, just triggered manually here instead of by Docker or an operator's `Ctrl-C`. No orphaned process, no corrupted log state; the interrupted run (run 24, stopped at 26/60 ticks) is a valid, if short, record like any other.

**Not yet done, flagged rather than silently skipped:** the exact upper ceiling (where `worker_connections` warnings start, analogous to the old single-worker 650-vs-800rps/path finding) hasn't been found for the 4-worker+zone config -- only that 500rps/path (the new default itself) sits comfortably under it, with no higher rate tested yet. Zone size (64k) and worker count (4) are both plain constants, not exposed as env-overridable the way `TICK_SECONDS`/`DEGRADATION_MEAN_DWELL_SECONDS` are -- no request yet to make them tunable, and 4/64k are working defaults, not something needing per-run adjustment the way backend timing does.

## `runs.log` format

Chosen as JSON Lines (one JSON object per run) rather than the pipe-delimited format used for NGINX access logs. The access log format is fixed-width by NGINX's `log_format` directive; `runs.log` has no such constraint, and JSONL lets a future algorithm's change-count key show up in new lines without breaking any code that reads older ones — matches "adding a new algorithm should be straightforward" elsewhere in this project.

## Operational gotchas found while testing Phase 1

- **Both Compose files share a project name.** Docker Compose derives the project name from the directory by default, not the `-f` filename — so `docker-compose.full.yml` and `docker-compose.controller.yml` run from the same directory land in the *same* project/volume namespace. That's intentional (see "same named volumes" above), but it means running `docker compose -f docker-compose.controller.yml up` while the full-mode stack's `controller` service is still up does **not** start a fresh controller-only container — Compose matches by project+service name and just reattaches to the one already running. Always `docker compose -f <the other file> down` before switching modes from the same directory.
- **The actionable validation-failure message has one source of truth.** `validate_backends.py`'s detailed failure report (which hosts, the full checked list, which file to edit, which Compose file to use) originally only printed from that script's own `main()`. `entrypoint.py` and `sampler.py` both call the lower-level `validate()` function directly and, before this was caught, only logged a bare Python list on failure — silently dropping the actionable message exactly where an operator would actually see it (container startup). Fixed by extracting `print_failure_report()` as a shared function all three callers use. If a new caller of `validate()` is added, it must call `print_failure_report()` on failure too, or this regresses again.

## Scaling

Nothing in `upstream-hosts.txt` parsing, NGINX config generation, or the sampler hardcodes a backend count — scaling from 5 to 10 to 25 backends in **`docker-compose.controller.yml`** (external mode) is purely editing `upstream-hosts.txt`. **`docker-compose.full.yml`** (local mode) is the exception: each locally-built backend is its own Compose service (so its specific `LATENCY_MIN_MS`/`LATENCY_MAX_MS`/`DEGRADATION_MULTIPLIER` tuning can differ), so adding local backends beyond the default 5 means adding both a service block here and a line in `upstream-hosts.txt`. This is inherent to Compose needing an explicit service per container instance, not a shortcut taken in the controller logic.
