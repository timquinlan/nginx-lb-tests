# nginx-lb-tests — Architecture & Design Notes

Describes the system as it exists today: what's running, how the pieces fit together, and why the code is built the way it is. See `README.md` for how to run it, `ALGORITHMS.md` for how ACO and Markov Chain work and why they were picked, and `FINDINGS.md` for experiment results.

## What's running, and where

Everything runs in Docker Compose. There are two Compose files:

- `docker-compose.full.yml` — builds and starts 5 backend containers plus the controller. Local dev / self-contained experiments.
- `docker-compose.controller.yml` — starts only the controller, pointed at external hosts listed in `upstream-hosts.txt`.

The **controller container runs NGINX itself** — there is no separate NGINX container. The controller's `entrypoint.py` validates backends, generates NGINX config, starts NGINX, primes algorithm state, and starts the per-algorithm sampling loops, all automatically on `docker compose up`. It does **not** run the traffic generator — that's a separate, manually-triggered step (see below).

## Language: Python

Controller and backend containers are both Python (stdlib-heavy, no frameworks). Chosen for fastest iteration on the ACO/Markov math and to share idioms with the analysis tooling (also Python). Tradeoff accepted: larger process footprint than a Go binary would give -- acceptable since this project's actual goal is measurement methodology, not production throughput.

## Entrypoint / orchestration model

`controller/entrypoint.py` runs, in order:

1. `validate_backends.py` logic — ping every host in `upstream-hosts.txt` with retries; exit non-zero on failure so `docker compose up` reports the container as failed.
2. `nginx/generate_config.py` — write each static algorithm's `.upstream.conf` and each dynamic algorithm's equal-weight-placeholder `.upstream.conf`, plus the main server conf.
3. Start NGINX as a background child process (`nginx -g "daemon off;"`).
4. `sampler.py`'s priming run: probe every backend directly (bypassing NGINX — there's no traffic yet), compute initial weights, write them via `config_writer.py`, which triggers `nginx -s reload`.
5. Start the per-algorithm sampling loops (background threads, one per dynamic algorithm) — these run continuously for the life of the container, rewriting weights and reloading NGINX every sampling window.
6. The entrypoint process then **supervises** NGINX: it waits on NGINX's child process and forwards `SIGTERM`/`SIGINT` to it, exiting with NGINX's exit code when it stops.

**NGINX is supervised, not `exec`'d.** NGINX has to already be running by step 3 so step 4 can `nginx -s reload` it — `exec`-ing into NGINX as the final step would either fail (port already bound) or start a conflicting second instance. Instead the wrapper stays alive as long as NGINX does and mirrors its exit code, which is what actually matters for Docker's health/lifecycle model.

**The traffic generator is invoked manually, per run:**

```sh
docker exec <controller-container> python3 traffic_generator.py --rps 5 --duration 10
```

`--duration` is in minutes (wall-clock), not ticks -- the script converts it internally to `ceil(duration*60/tick)` ticks, so a 10-minute run is just `--duration 10` regardless of `--tick`, instead of having to compute tick-count by hand.

This is why `runs.log` isolates multiple runs by start/end timestamp — the setup above happens once per container lifecycle; the operator can invoke additional traffic-generator runs against the same primed, continuously-adapting NGINX without restarting anything.

**Only one `traffic_generator.py` invocation is meant to run at a time (not enforced in code).** `next_run_index()` picks a run's index by counting existing lines in `runs.log` and adding one — two concurrent invocations against the same container would both read the same count and pick the *same* run index, then both send traffic to the same paths simultaneously with no way to separate one run's requests from the other's in the access logs afterward. Sequential runs (one at a time, back to back) are exactly what `runs.log`'s isolation-by-timestamp is built for.

**`--tick` and the container's `TICK_SECONDS` are two different channels.** `TICK_SECONDS` is read once at container boot by `sampler.py` (the sampling window size) and each backend (the degradation cycle length) — fixed for the container's whole life. `--tick` only controls the *traffic generator's own* status-line cadence and duration accounting for that one `docker exec` invocation; there's no live channel for it to reach the already-running sampling loops. `--tick`'s argparse default reads `common.TICK_SECONDS` (which already reads the env var), so leaving it unset always matches the real sampling cadence — an explicit override remains possible for the rare case where you want them to differ.

## NGINX layout

- Experiment traffic (all six paths -- `/rr_control`, `/leastconn`, `/aco_wrr`, `/mc_wrr`, `/aco_lc`, `/mc_lc`) is served on a **separate port from NGINX's stock default server** (`NGINX_EXPERIMENT_PORT`, default `8080`). The base image ships `conf.d/default.conf` — a `server { listen 80 default_server; }` block. Adding our own `listen 80` server would either conflict (duplicate default server) or silently never be reached (the shipped default wins). A separate port sidesteps this and leaves port 80's default location as a free, undisturbed liveness check.
- The controller's own generated confs (all six upstream blocks + main server block) do **not** live directly in `/etc/nginx/conf.d`. A volume mounted straight onto `conf.d` would overlay — and hide — whatever the base image put there (`default.conf` included) the first time the mount is used. Instead they live in `CONF_DIR` (default `/var/lib/nginx-lb-tests/nginx-conf.d`, bind-mounted from `./nginx-conf` on the host), and `generate_config.py` drops one small file *outside* that bind mount, directly into the real (image-backed) `conf.d`, that just does `include /var/lib/nginx-lb-tests/nginx-conf.d/*.conf;`. Cheap to regenerate identically every startup; never touches `default.conf`.
- DNS resolver directive is chosen by `DEPLOY_MODE`: `127.0.0.11 ipv6=off` (Docker embedded DNS) for `full`, `8.8.8.8` (public resolver) for `external`. This directive only actually governs re-resolution for *variable*-based `proxy_pass` targets; our upstream blocks use static `server host:port;` entries, which NGINX resolves once at config-load/reload time via the normal system resolver regardless of the `resolver` directive. In practice this doesn't matter for `aco_wrr`/`mc_wrr`/`aco_lc`/`mc_lc` (reloaded every sampling window, so DNS stays fresh as a side effect) but does mean the two static paths' upstream confs (`rr_control`/`leastconn` -- generated once, never reloaded) would keep routing to a stale IP if a full-mode backend container were recreated (not just restarted) mid-run.

## Log format and the `$upstream_addr` gotcha

Log format: `$msec | $uri | $upstream_addr | $upstream_response_time | $upstream_header_time | $status | $sent_http_x_degradation_offset_ms`.

- `$msec` is NGINX's only source of millisecond-precision timestamps — it's seconds-since-epoch with a millisecond decimal (e.g. `1721923200.123`), not a raw integer millisecond count. `$upstream_response_time` / `$upstream_header_time` are the same shape (e.g. `0.014`), despite this doc's field names using an `_ms` suffix for readability elsewhere. Multiply by 1000 if an integer ms value is wanted.
- **`$upstream_addr` is a resolved `ip:port`, never the original hostname.** `sampler.py` has to independently resolve each host in `upstream-hosts.txt` and build an `ip:port -> host` map (`common.resolve_ip_to_host_map`) before it can attribute access-log lines back to a named backend. This is re-derived at the start of every sampling window.

## Two data streams

- **Stream 1 (operational, not analyzed):** algorithm internal state (raw pheromone/transition-matrix values), fallback-probe notices — stderr only, not a deliverable. One exception: the *applied integer weight* per backend per window is also written to `{algo}.weights.csv` (see "Per-window weight history" below) specifically for the analysis tooling to use.
- **Stream 2 (the experimental evidence):** NGINX access logs + `runs.log`, on the `./logs` host directory (bind-mounted, not a Docker-managed named volume — see "Bind mounts, not named volumes" below). This is the primary input to `analysis/` (TTFB, selection frequency, etc.) — the weight history is supplementary detail explaining *why* the selection frequency looks the way it does, not a replacement for it.

## Per-window weight history

`config_writer.apply_weights()` appends every window's applied weights to `{algo}.weights.csv` (`aco_wrr.weights.csv`, `mc_wrr.weights.csv`, `aco_lc.weights.csv`, `mc_lc.weights.csv`, separate file per algorithm) — unconditionally, whether or not the weight actually changed from the prior window, so a time series has no gaps to fill in. Priming's initial weights land as the first row for free, since priming calls `apply_weights()` the same as every later window.

**Wide-form CSV**: `timestamp_ms, timestamp_iso, <one column per backend>` — one row per window, chosen so a line chart (x=time, y=weight, one line per backend) is a direct plot away with no reshape needed. Column order is fixed to the canonical `hosts` list from `upstream-hosts.txt`, not whatever order a given algorithm's internal dict happens to iterate that window — a wide CSV's columns have to stay stable for the life of the file. Both timestamp forms are written: epoch ms for precise sorting/joins against the access logs (which use `$msec`), ISO for a human to eyeball directly. Deliberately just the applied integer weight (what's actually in the `.conf` file), not the raw pheromone level or stationary probability behind it — keeps the file minimal and directly answers "what was NGINX actually doing."

**Known tradeoff, not engineered around:** if the backend pool in `upstream-hosts.txt` changes between container restarts that both append to the same (persistent, bind-mounted) `./logs`, the column set won't match the original header partway through the file. `read_weights_csv()` handles this defensively — a row it can't fully parse against the file's header is skipped (`try/except (TypeError, ValueError)`) rather than crashing the whole analysis, since the primary TTFB data (from `.access.log`, unaffected) shouldn't be held hostage by a secondary stat. Still, the expectation is to clear or rename `./logs` before a run against a genuinely different backend pool for a clean comparison.

## Bind mounts, not named volumes

`./logs` and `./nginx-conf` (repo-root directories, gitignored) are bind-mounted into the container rather than using Docker named volumes. Named volumes are opaque — reaching the data means `docker exec`/`docker cp` every time. Since this whole project's point is inspecting the experiment data, and the analysis scripts are meant to be runnable/adaptable directly, plain host directories you can `ls`/`cat`/point a local Python script at are more useful here. Both Compose files bind-mount the same host paths by design, so switching between full/controller-only mode doesn't lose data.

## Algorithm stub

`controller/algorithms/stub.py`'s `EqualWeightStub` is a minimal reference implementation of the `Algorithm` interface (equal weights, no learning) — left in the tree, unwired, as documentation of the interface's shape for anyone adding a new algorithm.

## Backend static-file stub

`backend/server.py` has a `/static` route for a future throughput-focused phase: if `STATIC_FILE_PATH` is set and points at a real file, it serves that file's bytes with the same degradation header as the default route; otherwise it returns `501` with a plain-text explanation rather than pretending to serve real content. No Compose file sets `STATIC_FILE_PATH` today, so this route always 501s in practice — the plumbing exists without being exercised by any current experiment. Setting `STATIC_FILE_PATH` (and mounting a file at that path) is all that's needed to turn it on.

## Backend degradation model

Each backend's simulated latency has two independent parts, both configured per backend in `docker-compose.full.yml`:

- **A fixed personality range** (`LATENCY_MIN_MS`/`LATENCY_MAX_MS`) — every request draws fresh jitter uniformly within this range. Backends have *distinct* ranges (see "Backend pool" in `README.md`), representing a heterogeneous hardware fleet, not a shared baseline. This matters for what the experiment can actually show: if every backend performed identically on average, there'd be no persistent structural difference for an adaptive algorithm to learn, and the honest answer would just be "use whatever's already standard." Distinct personalities are exactly the kind of asymmetry a static or purely-instantaneous baseline (`rr_control`, `leastconn`) can't see, which is what makes a genuine comparison against learned weighting possible.
- **A drifting, per-backend signed offset** (`DEGRADATION_OFFSET_MIN_MS`/`MAX_MS`, default `-10` to `+250`, shared range across backends) added on top of the personality draw: `total_latency_ms = max(0, base_jitter + offset_ms)`. Negative means currently faster than the backend's own baseline; positive means slower. The range is asymmetric on purpose — more physical room for a real backend to get much worse (contention, GC pauses, noisy neighbors) than to get much better (a floor set by the network/OS stack).

**The offset reshuffles on a randomized dwell, not a fixed clock.** Each backend has its own `DEGRADATION_MEAN_DWELL_SECONDS` (see the table in `README.md`), and each *visit* to a new offset draws its actual dwell from `random.uniform(0.5, 1.5) * DEGRADATION_MEAN_DWELL_SECONDS` — bounded, not exponential, so no implausibly long or near-instant dwell. This is deliberately decoupled from `--tick`/`TICK_SECONDS` (the algorithms' own sampling cadence): if the environment's change cadence were a fixed multiple of the sampling window, the two would be permanently phase-related, and a longer real run wouldn't dilute that coupling — it would just re-measure the same fixed relationship more precisely. Keeping them independent means `--tick` is a genuinely free variable to experiment with, not one that also silently rescales the ground truth. Every realized transition is logged to `./logs/degradation-{backend}.log` (`timestamp_ms,offset_ms,dwell_seconds`) as ground truth — reproducible via the logged realized timeline, not via predictability in advance the way the old deterministic version was.

**The tunable that actually matters is the dwell-to-window ratio, not any absolute value.** If `DEGRADATION_MEAN_DWELL_SECONDS` is too close to `--tick` (roughly under ~4x), most sampling windows either straddle a transition or get invalidated by the next one before an algorithm's newly-computed weights have a chance to matter — the algorithms' entire mechanism of advantage gets outpaced by the environment, collapsing every path toward statistically indistinguishable. This isn't a hypothetical -- it's why the project's current default tick (10s) sits comfortably above 4x the fastest backend class's dwell mean. Aim for at least ~4x the sampling window on the fastest backend class as a starting point, and re-derive if backend timing changes.

**Reported via `X-Degradation-Offset-Ms` on every response.** The NGINX log format, `analysis/log_reader.py`'s parsing, and the TTFB chart's overlay all key off this — the chart plots mean signed offset per window (an unbounded, zero-centered line with a reference line at 0), pooled across every discovered algorithm's records rather than one redundant line per path, since degradation is a property of the backend that served a request, not of which algorithm's location block routed to it.

## Analysis tooling (`analysis/`)

`analysis/` reads a selected run's access logs and weight-history CSVs and produces a stdout summary table plus PNG charts. See `analysis/README.md` for the log schema, run-isolation mechanics, and how to adapt it — this section covers the architectural decisions behind it.

**Deliberately independent of `controller/`, not an import of it.** `analysis/log_reader.py` re-implements the small amount of parsing it needs (access-log fields, `runs.log`, weight CSVs) rather than importing `controller/common.py`. Two reasons: (1) `analysis/analyze.py` is meant to be runnable directly from the host machine against the bind-mounted `./logs` directory — `controller/common.py` isn't on a host Python's import path, and several of its constants don't mean anything outside the container anyway; (2) keeping `analysis/` only assuming on-disk file formats, not this project's internal module layout, keeps it simple enough to adapt to a different algorithm or log schema.

**Naming note:** the analysis parsing module is named `log_reader.py`, not `common.py`, specifically to avoid colliding with `controller/common.py` — `traffic_generator.py`'s end-of-run hook imports both in the same process, and Python's `sys.modules` cache is keyed by bare module name regardless of `sys.path` order, so a same-named second module would silently shadow the first instead of raising an error. Any future module added under `analysis/` should avoid reusing a name that already exists under `controller/`.

**The end-of-run hook uses an in-process import, not `subprocess`.** `traffic_generator.py` adds `analysis/` to `sys.path` at startup and calls `analyze.run_analysis(...)` directly, avoiding paying Python + matplotlib's import cost via a fresh subprocess on every run. Analysis failures are caught and logged rather than left to propagate — by the time the hook runs, the traffic-generator run already succeeded and its record is already in `runs.log`, so a broken chart shouldn't be reported as a failed experiment run.

**`ip_to_host.json`** persists the `ip:port -> host` map `sampler.py` already builds every sampling window (see "$upstream_addr gotcha" above) to `LOG_DIR`, since that resolution depends on Docker's embedded DNS, reachable only from inside the container — `analysis/` (meant to also run from the host) reads this snapshot instead of re-resolving anything itself. This also avoids a subtler correctness issue: the snapshot reflects the exact mapping NGINX was actually using at the time, not a potentially-different one from a later lookup. A missing file (e.g. logs copied from elsewhere) degrades gracefully — backends are labeled by raw `ip:port` instead of by name.

**Charting: matplotlib, the one dependency in an otherwise stdlib-only project.** Chosen over hand-rolled stdlib-only SVG charts or CSV-only output, since line charts are an explicit deliverable, not a nice-to-have. Installed via `apt-get install python3-matplotlib` in the controller image rather than `pip` (Debian's system Python refuses global `pip install` under PEP 668, and matplotlib ships as a normal apt package). `analysis/requirements.txt` covers the ordinary `pip install` case for host-side use. `matplotlib.use("Agg")` is set explicitly in both plotting functions since the controller container has no display.

**Per-run config-change count is recomputed from `{algo}.weights.csv`, not read off `runs.log`'s `change_counts`.** `config_writer.py`'s change counter is cumulative for the life of the container (persisted in `{algo}.state.json`), so `runs.log`'s stored `change_counts` for any run is a running total, not "how many changes happened during that run" — reading it directly would double-count everything from prior runs. Instead, `log_reader.count_weight_changes()` filters `{algo}.weights.csv` to the selected run's `[start_ts_ms, end_ts_ms]` window and counts transitions between consecutive rows inside it (undercounting by at most one per algorithm per run, for a change landing exactly on the window boundary — accepted, not engineered around). The same cumulative-counter trap existed in `traffic_generator.py`'s own live per-tick status line (`current_change_counts()`) — fixed by capturing a baseline snapshot at the start of `run()` and printing `current - baseline` each tick instead of the raw lifetime value. `runs.log`'s own `change_counts` field is left as the raw cumulative snapshot, since nothing reads it directly for per-run stats.

**The analysis window size defaults to the run's own `tick_seconds`**, inheriting the same assumption `traffic_generator.py --tick` carries (see above): correct as long as `--tick` wasn't deliberately overridden away from the container's real `TICK_SECONDS` for that run. `--window-seconds` is exposed on `analyze.py` for the case where it was.

**`runN_stats_report.txt`** is a text file (not a chart) with TTFB mean/median/p90/p95/p99 per algorithm, every discovered algorithm ranked best-to-worst (tagged `[control]`/`[adaptive]`/`[built-in]`), each non-control algorithm's delta against the `rr_control` control, and an incremental comparison between the best-performing built-in algorithm and the best-performing adaptive one. `CONTROL_ALGO` (`rr_control`) and `ADAPTIVE_ALGO_NAMES` (`aco_wrr`, `mc_wrr`, `aco_lc`, `mc_lc`) are hardcoded rather than inferred, since group membership is a fact about the experiment design, not something derivable from which log files happen to exist. The ranking and best-built-in-vs-best-adaptive sections are computed before the control-comparison section's early-return check, so they still appear even if `rr_control` itself has no data for a run.

**Significance testing, not just deltas** — two tests, kept separate since they answer different questions:
- **Mann-Whitney U** (`log_reader.mann_whitney_u`) on the full TTFB samples — "is the whole distribution different from the control." Implemented by hand (normal approximation with tie correction) rather than reaching for `scipy`, since this is standard textbook material and a single sort stays sub-second even at real-experiment scale. Runs on the full, uncapped sample.
- **Percentile bootstrap confidence intervals** (`log_reader.bootstrap_delta_cis`) on each stat's delta — "is *this specific stat's* difference likely non-zero," flagged significant when the CI excludes 0. `capped_sample()` draws a reproducible random subsample (default cap 5000/side) before bootstrapping only, since bootstrap resampling (2000 resamples by default) doesn't scale the way a single Mann-Whitney sort does — point estimates and Mann-Whitney still see every request.
- **One alpha, not two.** `SIGNIFICANCE_ALPHA` (default 0.05) is both the Mann-Whitney verdict threshold and, as `1 - alpha`, the bootstrap CI's coverage — avoids the two tests silently drifting to different confidence levels with no flag that they differ.
- **Reproducible seeding:** the bootstrap's RNG is seeded from the run's own `start_ts_ms`, so regenerating a report for the same run reproduces the same CIs.

**On short runs, "not significant" is the expected, correct result, not a bug** — a few thousand requests over tens of seconds usually isn't enough to separate real algorithm differences from noise, especially against backends with deliberately overlapping latency ranges. See `analysis/README.md`.

## Shape charts (`analysis/shape_charts.py`)

Answers a different question than the rest of `analysis/`: not "how did one run go," but "does the picture change as rps changes, across a multi-run sweep, or is it flat." Built for a 15-run sweep (rps 20/40/80/160/320, 3 repeats each, run in the user's own terminal via `for i in 20 40 80 160 320 20 40 80 160 320 20 40 80 160 320; do python3 run_experiment.py run --rps $i; done`) but not hardcoded to that shape — see below.

**To rebuild:** `python3 analysis/shape_charts.py` from the repo root (needs the same host-side `matplotlib` as any other host-side use of `analysis/` — see `analysis/requirements.txt`). Optional `--run-min`/`--run-max` narrow the `run_index` range if `./logs` also contains older, unrelated runs. Writes `shape_means_by_rps.png` and `shape_deltas_by_rps.png` to `<logs-dir>/analysis`.

**Bucketing is automatic, not hardcoded to 5 rps values or 3 repeats.** `collect_run_means()` groups every clean (non-interrupted), in-range run by its own `rps_per_path` from `runs.log` — a future sweep with different rps values, a different repeat count, or even a single run per rps value still works; a bucket with only one run just plots one dot with no repeat spread rather than erroring.

**Recomputes mean TTFB from each run's raw access log** (`common.parse_access_log` + `common.mean`, the same path `analyze.py` itself uses for point estimates) rather than parsing any run's `runN_stats_report.txt`. Keeps this correct even if that report's text formatting changes later, and means a run doesn't need its own stats report to already exist.

**Chart 1 (`shape_means_by_rps.png`):** one line per algorithm, x=rps, y=mean of that rps bucket's repeat runs' mean TTFB. Each repeat's own value is also scattered as a small, same-colored, semi-transparent dot — a single mean-of-means line would erase exactly the repeat-to-repeat noise the "is there a real shape" question depends on seeing.

**Chart 2 (`shape_deltas_by_rps.png`):** two lines, `aco_wrr - mc_wrr` and `aco_lc - mc_lc` (mean TTFB delta in ms; negative = the first algorithm faster), same mean-line-plus-individual-dots treatment, with a dashed zero reference line. `DELTA_PAIRS` is the only place to edit if a different pair of algorithms ever needs the same treatment.

**Repeats are paired by position, not by value.** For the delta chart, `collect_run_means()` appends every algorithm's per-run mean in the same `runs.log` iteration order, so `vals_a[i]` and `vals_b[i]` in `plot_deltas_by_rps()` always come from the same run — `zip()` lines them up correctly without needing to carry `run_index` through explicitly.

**`ip_to_host.json` is loaded once and reused across every run in the sweep**, not re-loaded per run — every run sharing one `./logs` directory also shares one backend pool/network, so the resolved mapping doesn't change run to run. Same assumption `analyze.py`'s own single-run analysis already makes about the snapshot being current; just applied across runs here instead of within one.

First run of this (2026-08-06, the 15-run sweep above): both adaptive-vs-built-in and ACO-vs-MC margins held essentially flat across the 20-320rps range tested — the one soft exception was `aco_lc`/`mc_lc` converging toward a tie at rps=20 while staying ~3-5ms apart at rps≥40.

## NGINX process model: 4 workers, shared zones

`worker_processes` is `4` (`WORKER_PROCESSES_COUNT` in `controller/entrypoint.py`), and every upstream block carries an NGINX `zone` directive (`DEFAULT_ZONE_SIZE = "64k"` in `controller/nginx/upstream_conf.py`, one uniquely-named zone per algorithm — `rr_control_zone`, `leastconn_zone`, etc. — rendered unconditionally for every algorithm, not opt-in).

**Why a zone is required, not optional, once there's more than one worker:** NGINX keeps round-robin position, `least_conn`'s live connection counts, and `weight=`-based selection state independently *per worker process* by default. More workers without a zone means more independent cycles, each biased toward whichever backend it's currently pointed at — and since every fresh worker's cycle starts from the same first-configured server, the *aggregate* skew gets worse, not better, as worker count goes up. Confirmed directly (100 requests at 10rps to `/rr_control`, tallying `$upstream_addr` from the access log):

| Config | backend-1 | backend-2 | backend-3 | backend-4 | backend-5 | spread |
|---|---|---|---|---|---|---|
| 2 workers, no zone | 23 | 22 | 19 | 18 | 18 | 5 |
| 6 workers, no zone | 29 | 22 | 17 | 16 | 16 | 13 |
| 6 workers, **with zone** | 22 | 20 | 20 | 19 | 19 | 3 |

A `zone` directive puts that state in shared memory across all workers instead, collapsing the aggregate skew back down close to even (residual bias at only 100 requests is expected — not enough traffic for a single shared cycle to wash out its own start-of-cycle skew). This applies identically to every selection method used in this project (plain round robin, `weight=`-based weighted round robin, `least_conn`), which is why the zone directive is unconditional across every upstream block rather than opt-in per algorithm. `zone` itself is not an NGINX Plus feature — it's been available in open-source NGINX since 1.9.0.

**Zone data survives `nginx -s reload`, and so does everything already in flight.** Every algorithm's upstream conf gets rewritten and reloaded constantly here (`aco_wrr`/`mc_wrr`/`aco_lc`/`mc_lc` on nearly every sampling window). A reload is process-wide -- NGINX spawns an entirely new generation of worker processes for *every* location, not just the one whose upstream conf actually changed -- but it's a graceful, lossless event, not a disruptive one: the NGINX master process (which owns every zone's shared-memory segment) is never restarted, so zone contents -- connection counts, round-robin position, `least_conn`'s live state -- persist across the reload untouched, and old workers keep serving whatever they already had in flight to completion before exiting, uninterrupted. New workers are up and accepting connections before old ones stop, so a request arriving on an unrelated path during someone else's reload doesn't pay any reload-related latency either. Zone persistence only breaks if the zone's name or size changes between reloads, or the `zone` directive is removed outright — neither happens here, since `zone_name()`/`DEFAULT_ZONE_SIZE` are fixed constants for the container's life; only the `server ... weight=N` lines and method directives ever change between reloads.

**NGINX's default `worker_connections 1024` is a separate ceiling from CPU**, worth knowing about at high `--rps`: each proxied request holds two connection slots against that limit (one client-side, one upstream-side), so the practical ceiling is closer to ~512 concurrent proxied requests, not 1024. This is an ordinary NGINX tuning knob (`events { worker_connections N; }`, main-context like `worker_processes`) — raising it carries none of the round-robin-reproducibility tradeoff, since connection count doesn't affect which backend gets selected. A `1024 worker_connections are not enough` line in any `*.error.log` is the signal you've hit it; see `README.md`, "Choosing `--rps`."

**The traffic generator's thread pool is sized from the requested rps, not a fixed constant:** `workers_per_path = max(20, int(rps * 0.5))`, logged at run start. A fixed small pool would silently become the bottleneck at higher `--rps` — by Little's Law, a pool sized for a low rps can't sustain a much higher one given real backend latency, and `ThreadPoolExecutor.submit()` just queues faster than it drains rather than erroring, so the achieved rate would quietly fall short of the target with nothing in any log to flag it. Worth double-checking this margin whenever the backend latency profile changes significantly (a much slower backend pool needs more headroom per worker to hit the same target rps) — see `FINDINGS.md`'s caveats section for a case where the margin wasn't enough and throughput degraded continuously over a long run instead of settling at a lower-but-stable rate.

## History: multi-instance topology & contention mechanism (built, tested, removed)

A multi-instance topology (3 independent NGINX+controller instances sharing one backend pool) and a backend-side concurrency-cap mechanism ("contention": off/mild/moderate/heavy) were built and run through a 16-combination sweep (`--rps` 40/80/160/320 x contention off/mild/moderate/heavy) specifically to test NGINX's own documented caution that `least_conn`/`random two` aren't recommended when multiple independent load balancers share a backend pool, since each one's connection-count view is blind to what the others are doing. The result: `leastconn` kept winning by the same margin (growing with contention severity, but the same *direction*) at every rps/contention combination in the reasonable-TTFB range -- no distinguishable "many-LB blindness" effect showed up. The only ranking flip (at `--rps 320`) turned out to be a raw request-rate overload artifact, not a real multi-LB or contention effect -- see `FINDINGS.md`'s stability table for the numbers. Since the added topology/mechanism didn't surface a different substantive conclusion than the original single-instance experiments, both were removed afterward to keep the codebase simple -- the empirical result is preserved in `FINDINGS.md`, but `docker-compose.multi.yml`, `analysis/merge_analyze.py`, and the backend's `/admin/capacity` concurrency cap no longer exist in the tree. `run_experiment.py` survived this cleanup as a simplified single-instance convenience wrapper (see below).

## `run_experiment.py` (host-side convenience wrapper)

`run_experiment.py` (repo root) wraps the manual `docker exec ... traffic_generator.py` + `analyze.py` workflow described above into `run`/`status`/`analyze`/`purge` subcommands against `docker-compose.full.yml`'s controller -- see `README.md`, "Using `run_experiment.py`." `status`/`purge` detect whether a run is currently in progress via `find_active_traffic_generator()` (`docker top -eo pid,etimes,args`, looking for a live `traffic_generator.py` process) -- `purge` refuses to delete `./logs` out from under a live run, which would corrupt it (that run's own eventual `write_run_record()` call landing in a file whose line count no longer matches what its `next_run_index()` counted at startup).

## History: `/random` and `/random2` as validity canaries (built, tested, removed)

`/random` (NGINX `random`) and `/random2` (NGINX `random two`) existed as much to validate the measurement harness as to compare against -- kept deliberately even though `/random` vs. `/rr_control` was expected (and, every run, confirmed) to come back statistically indistinguishable, since an unweighted dice roll and unweighted round robin converge to the same distribution at scale. Two independently-implemented, mechanistically distinct NGINX code paths agreeing on every single run was stronger evidence the measurement harness itself was trustworthy than either result alone would have been -- see `FINDINGS.md`'s history for the numbers (p=0.21-0.97 across every run, never once significant). Once that validation purpose was fulfilled and the harness's correctness was no longer in question, both were removed to simplify the algorithm roster down to the pairs actually being compared (`rr_control`/`leastconn` static baselines, `aco_wrr`/`mc_wrr`/`aco_lc`/`mc_lc` dynamic). `random two least_conn` was, for the same reason `/random2` alone already covered it, never built as a separate path either -- `least_conn` is the *default* (and, in open-source NGINX, only) method for `random two`'s `two` parameter, so `random two;` and `random two least_conn;` are byte-for-byte identical directives, not just similar; building both would have been two paths mechanistically guaranteed to agree.

**Static algorithms are enforced by which tuple a name goes in**, not by any per-path special-casing downstream. `STATIC_ALGO_NAMES` (`rr_control`, `leastconn`) vs. `DYNAMIC_ALGO_NAMES` (`aco_wrr`, `mc_wrr`, `aco_lc`, `mc_lc`) in `controller/common.py` — everything that branches on these two tuples (NGINX config generation's static-vs-placeholder-weight split, the sampler's dynamic-only sampling loops, the traffic generator's dynamic-only change-count display, `read_location_paths()`, `analysis/log_reader.py`'s `discover_algos()`) picks up a new static or dynamic algorithm automatically, no code change needed beyond the tuple itself. `least_conn` is an upstream-block-level method directive, an entirely different selection mechanism from the `server host:port weight=N;` lines `/aco_wrr`/`/mc_wrr`/`/aco_lc`/`/mc_lc` use — `render_upstream_conf()`'s `method` parameter renders as the first line inside the `upstream {}` block when given, and `weights` stays `None` for the purely-static paths. The mapping from algorithm name to directive lives in `STATIC_ALGO_METHODS` (`{"rr_control": None, "leastconn": "least_conn"}`) — `None` for `rr_control` means no directive line at all, since round robin is just the upstream block's default with no method line. `aco_lc`/`mc_lc` are the two dynamic algorithms with a non-`None` entry in the analogous `DYNAMIC_ALGO_METHODS` (both `least_conn`) — see below.

## `aco_lc`/`mc_lc`: `least_conn` plus a learned algorithm's weights

`/aco_lc` and `/mc_lc`'s upstream blocks combine a method directive *and* `weight=` entries on the same conf — `render_upstream_conf()` already supported this (the two are independent `if`/`for` branches, never mutually exclusive in the code, just never combined in practice until these). Concretely: `least_conn;` as the method, plus integer `weight=N` on every `server` line, rewritten every sampling window by a dedicated ACO or Markov Chain instance respectively. NGINX's `least_conn` then picks the server with the lowest `active_connections / weight` — a live, zero-lag signal (same one `/leastconn` uses alone) with the algorithm's learned weighting biasing which backend wins a tie, rather than a lagged weight signal replacing the live one outright.

**Own instance, own state, not shared with the `_wrr` sibling.** `sampler.py`'s `ALGORITHMS` dict gives `aco_lc` its own `AntColonyOptimization()` instance (separate from `aco_wrr`'s) and `mc_lc` its own `MarkovChain()` instance (separate from `mc_wrr`'s), each fed by its own path's access-log window — deliberately not a shared reference to its `_wrr` sibling, so each `_lc` path stands on its own the same way every other dynamic algorithm here already does, and doesn't depend on its sibling also receiving traffic to have weights to apply.

**`aco_lc` shares `aco_wrr`'s tuning knobs today, not by choice so much as by the class not exposing per-instance overrides.** `ACO_EVAPORATION_RATE`/`ACO_DEPOSIT_CONSTANT` (`controller/algorithms/aco.py`) are read once as module-level constants at import time, so both `aco_wrr` and `aco_lc` always run with identical tuning within a given container — there's currently no way to hold one fixed while sweeping the other in the same run. Testing whether `aco_lc` wants different tuning than solo `aco_wrr` (plausible, since `least_conn`'s live signal is already covering the zero-lag reaction that `aco_wrr` alone has to earn through fast ticking) means either accepting that any tuning sweep run moves both paths together, or adding separate `ACO_LC_EVAPORATION_RATE`/`ACO_LC_DEPOSIT_CONSTANT` env vars and turning the two constants into per-instance constructor args -- not done as of this writing. MC has no equivalent tuning knob yet at all (see `EXPERIMENTS.md`), so the same question doesn't yet apply to `mc_lc`/`mc_wrr`.

**Counted as adaptive, not built-in, for analysis purposes.** `analyze.py`'s `ADAPTIVE_ALGO_NAMES` includes `aco_lc`/`mc_lc` alongside `aco_wrr`/`mc_wrr` despite their use of NGINX's own `least_conn` method underneath -- their weights are still a per-window algorithm output (weight-history CSV, change count, the works) the same as their `_wrr` siblings, they just bias a live NGINX mechanism instead of driving plain weighted round robin on their own.

See `FINDINGS.md` for the results this was built to test.

## `runs.log` format

Chosen as JSON Lines (one JSON object per run) rather than the pipe-delimited format used for NGINX access logs. The access log format is fixed-width by NGINX's `log_format` directive; `runs.log` has no such constraint, and JSONL lets a future algorithm's change-count key show up in new lines without breaking any code that reads older ones.

## Operational gotchas

- **Both Compose files share a project name.** Docker Compose derives the project name from the directory by default, not the `-f` filename — so `docker-compose.full.yml` and `docker-compose.controller.yml` run from the same directory land in the *same* project/volume namespace. That's intentional (see "Bind mounts, not named volumes" above), but it means running `docker compose -f docker-compose.controller.yml up` while the full-mode stack's `controller` service is still up does **not** start a fresh controller-only container — Compose matches by project+service name and just reattaches to the one already running. Always `docker compose -f <the other file> down` before switching modes from the same directory.
- **The actionable validation-failure message has one source of truth.** `validate_backends.py`'s detailed failure report (which hosts, the full checked list, which file to edit, which Compose file to use) is only ever printed via a shared `print_failure_report()` function, called by every caller of the lower-level `validate()` (the script's own `main()`, `entrypoint.py`, `sampler.py`) — not duplicated per caller, so a bare Python list on failure can't silently replace the actionable message at exactly the point an operator would see it (container startup). If a new caller of `validate()` is added, it must call `print_failure_report()` on failure too.
- **A foreground `docker exec` without `-i`/`-t` does not proxy signals to the remote process.** If the local invocation is killed (timeout, Ctrl-C), only the local CLI detaches — the process keeps running inside the container, invisible to the caller. Before starting a replacement `traffic_generator.py` run after any ambiguous failure, verify no instance is still running (enumerate `/proc/[0-9]*/cmdline` inside the container — works even in this minimal image with no `ps`/`kill` binaries) rather than trusting the local exit code. Two overlapping invocations collide exactly as described above ("only one invocation at a time") — doubled traffic into the same log files, and potentially enough combined memory pressure from two concurrent post-run analysis passes to get the container's cgroup OOM-killed.

## Scaling

Nothing in `upstream-hosts.txt` parsing, NGINX config generation, or the sampler hardcodes a backend count — scaling from 5 to 10 to 25 backends in **`docker-compose.controller.yml`** (external mode) is purely editing `upstream-hosts.txt`. **`docker-compose.full.yml`** (local mode) is the exception: each locally-built backend is its own Compose service (so its specific `LATENCY_MIN_MS`/`LATENCY_MAX_MS`/`DEGRADATION_MEAN_DWELL_SECONDS` tuning can differ), so adding local backends beyond the default 5 means adding both a service block here and a line in `upstream-hosts.txt`. This is inherent to Compose needing an explicit service per container instance, not a shortcut taken in the controller logic. ACO's weight scaling (relative to the current max pheromone, not the sum) and Markov's (direct scaling of an already-normalized stationary distribution) are both chosen specifically so neither algorithm's weight resolution degrades as backend count grows — see `ALGORITHMS.md`.
